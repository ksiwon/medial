# 04. 의료 요청·이슈·시나리오 라이브러리

## 1. '요청'보다 앞에 '필요'가 있다

Need → expressed/observed → request → contact → agreement → service/handoff → follow-up.

말을 안 한 사람도 필요를 가질 수 있다. 하지만 잠재 필요를 엔진에 넣었다고 MEDial이 감지한 것으로 처리하면 안 된다. 발생, 표현 여부, 표현 채널, 전달 성공, 시스템 인지를 각각 저장한다.

처음에는 연구자가 사건 카드를 편집하고 고정 deck으로 실행한다. 실제 발생률이 없으므로 균등 난수로 매일 질환을 만들지 않는다. 폭넓은 라이브러리와 높은 발생빈도는 다른 문제다.

## 2. 사건의 근거 구분

- source-adapted: 인터뷰/원본 데모의 돌봄 경험을 변환. 실제 해당 날짜의 사건이라는 뜻은 아님.
- plausible-extension: 자료의 어려움에 연결해 만든 설계 가설.
- stress-test: 용량 부족·통신 실패·정보 모순 등을 의도적으로 주입.
- emergent: 실제 실행 결과에서 파생된 사건. 앞선 event IDs가 필수.

원본 Q1/Q2/Q3/Q4/Q5를 실행하는 두 모드를 분리한다.
- replay: 기존 수행자·시간·결과를 그대로 재생.
- experiment: 원래 요청의 시각·맥락만 넣고, 원본 수락·이동·완료는 입력에서 제거.

## 4. 이슈 생성 엔진

| 이슈 | 발생 방식 | 탐색할 설계 질문 |
|---|---|---|
| 밭/배/가게에서 연락 불가 | 일과·채널 조건에서 파생 | 재연락이 나은가, 다른 채널/시간이 나은가? |
| 119 불빛으로 상태 노출 우려 | 근거 있는 상황 카드 + 에이전트 표현 | 공개를 줄이며 긴급 인계를 유지할 방법은? |
| 같은 도우미에게 두 요청 | 예약/업무량 결과에서 파생 | 묶음 수행·다른 후보·미해결의 비용은? |
| 이장에게 확인이 몰림 | 라우팅 정책 결과에서 파생 | 이장 경유가 필요한 상황과 직접 연결할 상황은? |
| 보건소 대기 누적 | 검토시간·인력·유입 사건에서 파생 | 감지 확대에 맞는 업무 분담은? |
| ASR 지명/증상 오인 | 주입된 채널 오류; 원 발화 별도 보관 | 확인 질문으로 정정 가능한가? |
| 센서 오래됨/미수신 | event timestamp·TTL·연결 상태 | 오래된 값을 최신 상태로 믿는가? |
| 서로 다른 관측 | 각 actor의 시각·전달 내역 | 모순을 누구에게 확인할 것인가? |
| 철회·거절 후 재권유 | 주민 행동·정책 조건 | 거절 존중과 미해결 필요를 함께 표현하는가? |
| 비참여 주민이 도움 가능 | 외부 자원 가용성 가정 | 12명 내 후보 없음과 마을 전체 후보 없음을 구분하는가? |
| 연구자 질문으로 행동 바뀜 | intervention branch | 관찰과 개입을 구별할 수 있는가? |
| 이동 중 다른 요청 | 현재 route/차량 좌석 | 재배정·회차·예약 충돌을 올바르게 계산하는가? |

연구용 시나리오 생성 LLM은 새 episode 후보를 쓸 수 있지만, 필요의 유형·위치·시간·빈도·기관 권한·근거를 검증한 뒤 연구자가 deck에 넣는다. 생성기가 미래 정답·수락자·결과를 시뮬레이션 주민에게 전달하면 안 된다.

## 5. 사건 카드 필수 필드

id, provenanceClass, sourceRefs, hypothesis, targetActors, trigger, hiddenTruth, observableSignals, channel, onset, validWindow, requiredCapabilities, requiredResources, consentScope, actorKnowledge, followUpTriggers, prohibitedInferences.

- hiddenTruth는 엔진 평가용이다. 주민에게도 자기 경험으로 표현될 정보만 준다.
- 사람의 진단명 대신 “도움이 필요한 상황”을 최소 단위로 쓸 수 있다.
- 발생 시각·예약 시각·서비스 희망 구간은 분리한다.
- 사건 템플릿은 정답 행동이나 성공 결과를 포함하지 않는다. 전문가 검토 기준은 별도 evaluator용 파일.

## 6. 첫 세 가지 완결 시나리오

### A. 09:30 P1의 무응답

WorldTruth: P1은 밭. 집의 장치에서 응답 없음.
MEDial: 해당 시각의 무응답만 수신. 밭 위치는 직접 알려지지 않음.
비교: 즉시 이장 연락 / 선호시간 재연락 / 최근 관측 확인 후 단계적 조율.
관찰: 연락 수, 추가 개인정보 공개, 이장 확인 시간, 필요를 놓친 시간.
핵심: 낮 무응답을 응급으로 자동 분류하지 않되, 상태 악화 신호를 별도로 받은 경우 다른 경로로 전환.

### B. P3의 두 부탁과 P9의 귀가

입력: P3의 기본 귀가 일정, 약 수령 지원 필요, P9 귀가 희망.
수락·동승·도착을 미리 써두지 않는다.
비교: 한 요청씩 먼저 가능한 사람 / 예약된 여유시간 고려 / 묶음 조율+조건부 수락.
관찰: 수혜자 대기, 도우미 추가 시간, 이동 경로, 거절 이후 미해결, 일정 복귀.
핵심: P3의 두 번째 수락이 첫 번째 약속의 시간 비용을 반영하는가?

### C. 긴급 연락과 전문 인계

입력: 원본 긴급 사례에서 채택한 신호, 신고 가능 채널, 원본 AMB를 참고한 명시적 출동시간 가정.
비교: 정보 확인 순서·최소 인계 정보·현장 안내 연결 방식. 긴급 연락을 일부러 지연시키는 정책을 추천 대상으로 삼지 않는다.
관찰: 접수 확인, 중복 연락, 잘못된 안내, 인계 필드 누락, 이웃/기관 역할 혼동.
핵심: 이웃 도착이나 MEDial 메시지 전송을 전문 인계 완료로 착각하지 않는가?

## 7. 며칠을 어떻게 돌릴 것인가

- 처음 1일: 원본 기반 소수 사건으로 원인과 결과 추적.
- 다음 3~7일: 예약·피로·연락 이력의 누적을 살펴보는 연구 가정 실행.
- 장기 30일: 실제 빈도·요일·계절·자원 분포가 확보되거나 명시한 민감도 실험일 때만.
- 같은 응급 상황을 매일 같은 주민에게 반복하지 않는다.
- 원본 숫자의 반복은 실제 장기 발생률을 추정해주지 않는다.

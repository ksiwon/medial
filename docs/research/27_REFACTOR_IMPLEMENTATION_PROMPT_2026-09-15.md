## 1. 작업 목표

Resident Agents as Evaluators의 핵심 연구 흐름을 사용자 경험과 코드 구조의 중심으로 만들어라.

인터뷰 근거 → 주민의 모의 서비스 경험 → 근거 있는 주민 평가 → 사람이 확인한 운영 규칙 변경 → 같은 조건의 재실행 → 평가 변화와 실패 경계 → 실제 주민에게 확인할 질문 및 이후 정정 기록.

최종적으로 만들어야 하는 것은 이 흐름을 수행하고 반박 가능한 근거를 남기는 연구 도구다. MEDial은 평가 대상인 첫 서비스다. 코드를 전면 재작성하거나 범용 사회 시뮬레이터를 만드는 작업이 아니다.

## 3. 반드시 지킬 연구 경계

- 주민 평가는 scoreless이고 simulated다. 긍정/혼합/부정/모름을 총점·순위·승자·자동 채택으로 바꾸지 마라.
- 주민은 본인이 경험한 사건과 허용된 인터뷰 근거만 인용한다. 세계 진실·타인의 비공개 사건·미래 사건을 섞지 마라.
- 사례·주민·관계·세계·외생 사건·자원·평가 기준은 동일 비교에서 고정한다.
- 저장한 초안은 실행 권한이 아니다. 연구자의 이유 있는 확정만 새 revision 하나를 실행한다.
- 모델의 실패를 규칙 답으로 대체하지 마라. 주민 LLM을 규칙표에 맞추도록 prompt를 임의 변경하지 마라.
- 규칙표 불일치를 실제 주민 불일치라고 쓰지 마라. 사람 검토 전 AI 라벨은 초안이다.
- 원자료·실명·민감 정보를 프런트 번들이나 공개 fixture에 복사하지 마라.
- 기존 실행·평가·인간 응답은 보존하고 정정과 수정은 새 기록으로 남겨라.
- 119, 다일 기억, 자유 주민 채팅, 장식적 3D, 다건 자동 최적화, 범용 DSL은 추가하지 마라.

## 4. 수행 순서

26번의 Phase 0~5를 순서대로 수행하라. 각 단계는 설계 설명에서 끝내지 말고 코드·검증·문서를 함께 완료하라. 장시간 작업이 필요하면 현재 단계와 남은 인수 조건을 기록하며 계속 진행하라.

### Phase 0

현 기준선과 보존 대상을 확인한다. 테스트와 합성 fixture로 실행·근거·확정 동작을 확보하고 비파괴 DB migration 전략을 적는다. 기존 실패를 리팩터링 결과로 숨기지 마라.

### Phase 1

F01을 먼저 해결하라. afterRule 문장과 executionBindings를 독립 편집하는 구조를 제거한다. 지원 ruleType별 typed semantic change가 UI 입력·전후 문장·검증·binding·semantic hash를 생성하도록 하라. 자유문장은 이유이며 실행 규칙이 아니다.

유효 AI 초안이 없어도 지원 규칙에서 직접 작성 가능하게 하고, '이번에는 수정하지 않음'을 제공하라. 저장 실패 시 입력을 보존하고 숫자/boolean/enum/목록은 타입에 맞는 컨트롤을 사용하라. 저장과 실행의 명령을 분리하라.

### Phase 2

기본 화면을 '사례와 서비스 경험 / 주민 평가 / 개선과 확인'으로 정리한다. 실행이 끝나면 주민 평가를 중심으로 안내하라. 평가→사건/인터뷰 근거→원래 평가로 돌아오는 맥락을 보존하라. 기본은 초기안과 수정안 한 쌍이다. 지도·재생·연구 설정·감사 기능은 필요한 수준에 배치하라.

### Phase 3

공동체의 ID·역할·관계·근거·일과·연락/거절 조건을 CaseBundle로 분리하라. 신규 자료에 이장 전지 가정이나 기존 P번호 관계를 자동 주입하지 마라. 기존 MEDial 동작을 보존하면서 ServiceAdapter 경계를 만들고, 이장 없는 새 ID의 5인 합성 공동체와 제한된 비의료 합성 서비스 하나로 같은 평가 루프의 이전 가능성을 검사하라. 공통 엔진에 새 서비스 이름 if문이나 복제 UI를 추가하지 마라.

### Phase 4

실행 규칙의 지원/적용/효과를 구분하고 manifest로 비교 조건을 검사하라. 종합의 원본 평가 참조, 제외된 주장, 의미 근거 검토와 라벨 주체를 남겨라. 인간 검토는 독립 응답→모의 평가 공개→항목별 일치/정정/충돌/모름 순서로 기록한다. 응답자와 장면 대상 주민, 자료 정정과 서비스 수정, 주민 응답과 연구자 메모를 구별하라.

### Phase 5

큰 엔진·화면의 책임을 분리하고 중복 신규 실행 경로와 폐기 타입·API·fixture를 함께 제거하라. 고유 감사 조회와 과거 데이터는 보존하라. API 타입 생성과 읽기 상태 일관성을 정리하라. 성능은 같은 fixture로 측정하고 측정하지 않은 개선을 주장하지 마라. DEVELOPMENT와 README는 현재 상태를 한 번만 설명하고 과거 이력은 별도로 연결하라.

## 5. 검증 방법

26번 8~9장의 인수 조건을 체크리스트로 사용하라. build·프런트·서버 검사를 실제로 실행하고, UI는 합성 DB의 실제 브라우저에서 확인하라. e2e reset이 연구 DB를 지우지 않도록 경로를 검증하라.

특히 다음을 빠뜨리지 마라.

- 문구 2회/실행 1회 같은 의미 불일치가 구조적으로 발생하지 않는가.
- 초안 없는 직접 작성, 저장 실패 복구, 변경 안 함이 가능한가.
- 저장 실행 0회, 중복 확정 실행 1회인가.
- unknown/미경험/거절/무응답이 구별되고 사적·미래 근거가 누출되지 않는가.
- 바뀐 규칙이 실행되지 않았을 때 '효과 없음'으로 오해시키지 않는가.
- 새 ID·이장 없음·장부 없음의 사례에 기존 마을 지식이 들어가지 않는가.
- 인간 응답 공개 전후·출처·명시적 충돌·정정 이력이 보존되는가.
- 1440×900, 1366×768, 800px 폭 및 키보드 조작에서 읽기와 근거 왕복이 가능한가.

실제 모델 검사는 기록 재생과 새로운 호출을 구분하고 당시 유효한 설정과 제한된 예산을 사용하라. 할 수 없었던 모델·브라우저·실제 사용자 검증을 완료라고 쓰지 마라. 형성평가 목표 시간은 자동 테스트로 입증된 사용성 수치가 아니다.

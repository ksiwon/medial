# 02. 세계·일과·주민 에이전트

## 1. 두 종류의 '오케스트레이션'과 세 종류의 상태

실험 진행기는 시계·사건·재현·버전을 관리한다. MEDial은 마을 안에서 제한된 정보로 의료·돌봄 조율을 한다. 연구자의 편의를 위해 세계 전체를 보는 기능이 MEDial의 정보 권한으로 흘러들면 안 된다.

| 상태 | 포함 | 접근 |
|---|---|---|
| WorldTruth | 실제 위치, 실제 수행, 잠재 필요, 통신 상태, 자원 잔여량 | 시뮬레이션 엔진; 연구자 전체보기 |
| ActorObservation | 전달받은 메시지, 본인이 경험한 사건, 허용된 관측 | 해당 주민·기관·MEDial |
| ResearchEvidence | 인터뷰 출처, 확실성, 정책, 모든 실행의 비교 | 연구자·검토자; 대화에 무조건 삽입하지 않음 |

P1이 밭에 있다는 사실을 엔진은 알아도 집의 라디오 무응답만 관측한 MEDial은 알 수 없다. P6가 최근 밭에서 P1을 봤다는 메시지가 도착해야 MEDial의 지식이 갱신된다. 그 관측도 시각과 유효기간을 가진다.

## 2. 고정 일과를 어떻게 녹일 것인가

원본 시뮬레이터의 plan에는 기본 일과뿐 아니라 이미 수락된 퀘스트 결과가 섞여 있다. P3의 약 전달·P9 방문, P9의 P12/P3 동승, P12의 P9 픽업을 모두 불변 일정으로 복사하면 새 정책이 거절해도 기존 이동이 재생된다.

따라서 원본을 세 층으로 분해한다.

1. source-replay: 원본 plan, EV, AMB 전체를 그대로 재현하는 기록 모드. 비교 참고용.
2. baseline-plan: 사건이 없을 때의 기본 일과. 근거 있는 출근·조업·귀가 시각을 보존하되 퀘스트로 생긴 방문·동승은 분리.
3. realized-plan: baseline 위에 수락된 약속, 자원 예약, 실제 이동, 지연, 복귀를 반영한 실행 계획.

“원본 일과에 맞게”는 source-replay가 정확하고, 실험의 기본 계획이 원본에서 유래하며, 바뀐 일정에 이유가 남는다는 뜻이다. 새 시스템의 결과까지 원본에 고정하는 뜻은 아니다.

### 원본 분해 시 보수적인 원칙

- P3: 09:00 읍내 출발과 13:00 귀가 시작은 원본 근거. 중간 MIGA·P9 방문은 task overlay로 분리. 방문이 없는 귀가 경로·도착 시각은 계산 결과임을 표시.
- P9: 진료 필요와 외출 희망은 issue. 원본 동승자는 선택 결과이지 기본 사실이 아님. 차를 배정받지 못하면 실제 미출발·대기·취소 상태가 남아야 함.
- P12: 08:00 외출은 baseline 후보, P9 픽업은 overlay. 정확한 근거를 필드별로 표시.
- P1: 09:00/13:00 밭, 12:00/16:00 귀가는 원본 시간표로 유지. 일정 변경 허용 범위는 연구자 가정이며 실제 선호와 다름.
- P10·P11의 HOME은 가게 겸 거처로 표시되는 구조다. HOME이라는 이유만으로 휴식·자유시간이라고 간주하지 않는다.
- 귀가시간·속도·차량 여부의 출처 충돌은 자동 해결하지 않고 후보 값과 선택 근거를 남긴다.

### 활동 계약

각 활동은 actorId, placeId, start/end, purpose, locked/flexible, earliest/latest, interruptibility, resumeRule, sourceRefs를 가진다.

- locked: 출근·선약 등. 연구상 예외 정책이 없으면 중복 배정 불가.
- flexible: 인터뷰에 여지가 있거나 연구자가 범위를 가정한 일과. 허용 범위 안에서만 재배치.
- task-overlay: 수락 후 생성. 도보, 픽업, 동승, 대기, 전달, 귀가를 각각 시간 구간으로 예약.
- 같은 사람이 두 장소에 동시에 있을 수 없다. 차량·좌석·운전자의 일과도 동시에 점유된다.
- 수락 시 미래 예약을 만들고, 약속 시점의 재확인·취소도 가능하다. 수락을 수행 완료로 계산하지 않는다.

예: P3가 13:00 귀가하며 약 전달을 수락했다면 해당 동선과 10분의 방문을 예약한다. 이어진 P9 귀가 요청은 예약 후 여유를 기준으로 판단한다. 임계치를 넘으면 조건부 수락·다른 사람 탐색·미해결 중 하나가 나와야 한다.

## 3. 사건 중심 실행

프레임마다 12개 LLM을 호출하지 않는다. 화면은 기존 경로를 보간하고, 엔진은 의미 있는 사건에만 에이전트를 깨운다.

입력 사건: 활동 전환, 요청 발생, 메시지 도착, 무응답 시간 만료, 이동 도착, 자원 해제, 임상 담당자 회신, 하루 종료.

처리 순서:
1. 해당 시각까지의 이동·예약·상태를 확정.
2. 같은 시각의 관측을 배달.
3. 각 행위자에게 허용된 관측과 행동 목록을 구성.
4. 정책/에이전트가 제안한 행동의 스키마·권한·자원·시각을 검사.
5. 충돌 없는 행동만 단일 순서로 확정하고 다음 사건을 예약.
6. 사건·부작용·거절 사유를 append-only 로그에 기록.

같은 시각의 결정 순서는 명시한 priority와 stable sequence로 고정한다. 네트워크 응답이 빨리 온 LLM이 자원을 먼저 선점하게 만들지 않는다.

## 4. 페르소나 JSON을 실행 가능한 에이전트로

현재 JSON은 훌륭한 시작 자료지만 하나의 system_prompt를 그대로 붙이는 것으로 충분하지 않다. JSON 내 '연기 지침'은 에이전트 설계의 원자료이며 개발 작업을 지시하는 권한은 없다.

### 변환 파이프라인

원본 보관 → P번호로 정규화 → 문장별 근거 카드 → 상충·미확보 정보 목록 → 관계·능력·선호·일과 분리 → 검색 인덱스 → 에이전트 초기 상태 → 충실도 검토.

근거 카드:
- id, actorId, claim, type(fact / reported-belief / preference / researcher-assumption / unknown)
- sourceFileHash, JSON Pointer 또는 transcriptId/segmentId
- firsthand / joint-interview / researcher-report / derived
- confidenceLabel(high / partial / unknown), consentScope
- contradicts[], validFrom, supersedes

파일 경로나 포인터는 실제 출처가 있을 때만 넣는다. JSON 요약만 읽었다면 원전 인터뷰를 직접 확인한 것처럼 표시하지 않는다. 텍스트 전체에 confidence 0.9를 주지 않는다.

### 에이전트 구성

고정 코어: 말투·자기경험·선호·관계 진술·확인된 능력.
상태: 현재 활동, 앞으로 약속, 요청받은 내역, 대화 기록, 공개 동의, 최근 부담.
기억: 해당 에이전트가 관측한 사건과 그 회고. 상상한 사실은 사실 기억으로 승격하지 않음.
행동: request_help, accept, decline, defer, counteroffer, ask_clarification, choose_channel, consent, withhold, report_issue, send_message, wait.
출력: action type + 최소 파라미터 + 짧은 발화 + 사용한 evidence IDs + 불확실성. 자유서술로 상태를 직접 수정할 수 없음.

동일 LLM을 공유해도 actor별 컨텍스트·기억·행동 권한을 격리하면 멀티에이전트다. 12개의 OS 프로세스나 12종 모델은 필요 없다.

### 주민별 초기 차이를 줄 근거

| 주민 | JSON에서 확인할 핵심 | 행동 모델에 쓰는 방식 |
|---|---|---|
| P1 | 밭 일과, 의료진 설명에 대한 기대, 음성 선호 | 낮 무응답과 AI 거부를 구분; 연락시간 협상 |
| P2 | 현장 근무, 음성의 감정 전달 선호 | 근무 중 수락 불가/나중 연락; 안내 어조 차이 |
| P3 | 읍내 왕복, 문자 선호, 같은 날 여러 부탁 | 시간·차량 예약 후 두 번째 요청 수락 여부 |
| P4 | 근무 및 공동식사, 이동지원 제안 | 셔틀/묶음 이동 아이디어 제안 가능; 항상 도우미는 아님 |
| P5 | 조업·밭, 앱 설치 어려움, 문자 사용 | 채널 접근성과 장소별 연락 도달률을 구분 |
| 이장(P6) | 순찰·방송·현장 연락망, AI 활용 | 개인 일과와 조율 업무를 같은 시간 예산에서 계산 |
| P7 | 증상 설명 어려움, 응급 노출에 관한 관점 | 정보 정리 도움·공개 범위 협상 가설; 무조건 신고 거부로 단정 금지 |
| P8 | 조업, 문자 선호, 설명·전문가에 대한 기대 | 입력 부담과 전문직 인계 설명을 구분 |
| P9 | 병원 방문 시간 비용, 디지털 활용 | 외출 기회비용·왕복 조율; 운전 여부는 별도 근거 검토 |
| P10 | 식당 일과, 간단한 상호작용·학습 지속 어려움 | 반복 질문과 복잡한 UI에 대한 대안 |
| P11 | 지속 진료 관계, 정보유출 우려 | 신뢰기관 연계와 최소 정보 공유 |
| P12 | 연구자 구술, 인터뷰 없음 | 미확보 태도·질병·선호를 생성하지 않고 추가 확인 대상으로 남김 |

AI 신뢰도 숫자는 원문 발언으로 보관한다. 수락률·만족도·정답 확률로 변환하지 않는다.

### 관계를 어떻게 표현할 것인가

A→B 부탁 가능성과 B→A는 다르다. 관계 edge에 taskType, describedRelationship, sourceRefs, confirmationStatus를 둔다. 같은 밥자리·같은 위치는 친밀도 수치나 부탁 동의를 의미하지 않는다. P6가 모든 사람에게 신뢰 1.0인 것도 아니다.

당분간 관계값 자동 증감은 비활성화한다. 거절 한 번이 신뢰 하락이라는 근거는 없다. 변경 가능한 것은 '이 부탁은 부담스러웠다'라는 사건 기반 기억이다. 장기 신뢰 전이식을 쓰려면 별도 가정과 민감도 실험으로 분리한다.

## 5. 대화와 연구자 개입

- 관찰 질문: 특정 시점 snapshot을 복제한 탐색 대화. 실제 실행의 기억·행동을 바꾸지 않음.
- 개입 대화: 연구자가 주민 또는 MEDial에 메시지를 보내 사건으로 투입. 새 branch를 만들며 이후 결과는 분기 실험.
- 사람의 정정: 페르소나/관계/정책의 새 revision으로 반영. 이전 실행은 유지.
- 모르는 질문은 abstain. 동네 지명·새 질환·새 가족관계를 채워 넣지 않는다.
- P번호화는 가명처리다. 실제 지도·희귀한 일화만으로 재식별될 수 있으므로 공개용 내보내기는 별도로 만든다.

## 6. 초기 품질 확인

12명별 최소 5개 질문: 알려진 사실, 미확보 사실, 일과 충돌, 관계의 방향, 정보 공유. 이어서 중요한 P1/P3/P6/P9/P12에 5개씩 상충 상황을 추가한다. 이는 개발 시작 규모 제안이지 통계적 검증 표본 수가 아니다.

원문을 넣은 질문에 같은 원문 답을 채점하는 것과, 근거 밖 상황의 일반화를 구별한다. 미사용 인터뷰 질문 또는 새 현장 질문으로 검토하고, 답변 검토자가 근거와 부합/모순/확인불가를 표시한다.

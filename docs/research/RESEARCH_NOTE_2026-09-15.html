MEDial · Research Note · Resident Agents as Evaluators

마을이 모델로 말하고, 연락 순서를 다시 세우다

은점마을 시뮬레이터에서 MEDial 머리와 주민을 실제 LLM으로 붙이고, 실제 모델로 같은 하루를 반복해 돌리다가 드러난 구멍(재연락이 실행되지 않음 · 빈집에서 요청이 닫힘)을 고친 이틀의 기록이다. 각 로직이 무엇을 하고, 왜 그렇게 정했고, 무엇으로 확인했는지를 결정 번호(D076–D089)와 함께 남긴다.

여기 나오는 주민은 모두 시뮬레이션 에이전트다. 실제 참여자가 아니며, 실행은 전부 합성 마을 (fixtures/synthetic/)에서 했다. 주민의 말은 모델이 만든 출력이다.

1. 지키는 원칙

아래 로직은 전부 이 원칙들 안에서 정했다. 결정이 헷갈릴 때 되돌아오는 기준이다.

연구자 지시

뒷단은 엄밀하게, 화면은 딱 직관적이게

내부 로직은 복잡해도 되지만, 디자이너가 보고 만지는 면은 단순하고 최소로. 화면에 새 노브를 늘리지 않는다.

적용 재연락·관계 우선·빈집 다음은 전부 엔진 안에서 해결하고, 화면은 그 결과를 문장으로 읽기만 한다.
연구 설계

점수로 합치지 않는다

신뢰 점수·수락 확률·합산 점수를 두지 않는다. 합치면 "잰 것"과 "추측한 것"이 구분되지 않는다.

적용 거절은 순서 있는 규칙 목록(D076), 결과 비교는 사람별 시간·연락 횟수를 나란히.
연구 설계

실패는 실패로 남긴다

모델이 조건을 어기거나 응답하지 않으면 규칙 답으로 바꿔치우지 않는다.

적용 한 번 되돌림 후에도 어기면 adapter_error. 규칙표는 옆에 기록만(D083).
자료 원칙

지어내지 않는다

원자료에 없는 조건·관계·장소를 만들지 않는다. 기록이 비어 있으면 비어 있다고 말한다.

적용 관계 우선 정책은 기록된 관계만(D087). 짐작할 지식이 없는 사람에게는 "어디 있을까"를 묻지 않는다.

2. 한 건의 흐름 — 지금 엔진(0.4.0)에서

덱 deck-p1-no-response-v1: 09:30 P1의 정기 안부 연락에 응답이 없다. 초록 번호가 이번에 새로 생긴 단계다.

1

안내 시계로 연락 → 응답 없음

MEDial은 "응답이 없다"만 안다. 왜인지(P1이 밭에 있다)는 연구자 전용 사건 world.reachability_resolved에만 있다.

2

상황 읽기 (read)

위치·몸 상태 모두 unconfirmed. 확정하려면 근거 사건 id를 대야 한다. 응급 근거가 없다는 것은 "응급이 아니다"가 아니다.

3

재연락 — retryCount만큼 전화로 D086

어떤 연락 순서든 먼저 실행된다. 코드가 하고, 모델 머리에게 할지 말지 묻지 않는다.

4

누구에게 부탁할지 (decide)

정책의 연락 순서(이장 우선 · 이웃 우선 · 관계 우선 · 보건소)에 따라. 모델 머리는 후보까지 고르고, 코드가 울타리를 검사한다(D082).

5

부탁받은 사람의 답

수락 · 거절 · 나중에 · 기록된 관계로 넘김. 거절하면 순서의 다음 사람에게, neighbourAskLimit까지.

6

집에 가 봄 → 있으면 해결

"그 장소에 있는가"만 확인한다. 건강 상태 판정이 아니다.

7

빈집이면 — 짐작 가는 곳을 아는가 D088

간 사람이 장소 단위 지식을 가졌으면(이장) 그가 말한다. 아니면 MEDial이 이장에게 전화로 어디 있을지 묻는다.

8

그곳으로 확인을 이어감 → 해결 / 미해결

이장도 짐작이 없거나, 이장에게 물을 수 없는 정책이면 미해결로 닫는다(인계 기한이 남았으면 기다린다).

3. 마을의 하루 — 같은 일과의 반복 D080

연구자의 전제: "시골 마을은 매일 똑같은 일상을 반복한다. 바리에이션은 약간뿐이다."

환경출발 시각 흔들림외출 생략외출 반복쓰임
env-v3 기본±10분00보통의 하루
env-v3-fixed없음00메커니즘 테스트용 고정 하루
env-v2±15분0.150이름으로 골라야만 쓰임
왜 바꿨나: v2의 외출 생략 확률 0.15는 12명 마을에서 거의 매번 "외출 하나가 다른 하루"를 만들어, 예외가 기본이 되어 있었다. 하루 변이는 dayRealization으로 기록되고 화면에 "기록된 시각이 조금 다른 하루"로 보인다.

4. 거절 — 규칙 목록, 점수 없음 D076 D077 D078

거절 사유는 순서 있는 규칙 목록이고, 먼저 걸리는 한 줄이 이유가 된다. 여러 줄이 동시에 걸려도 답은 하나다.

순서규칙 키화면 말근거의 성격
1persona_condition본인이 말한 조건인터뷰 (예: 영업 중 가게를 비울 수 없다)
2cannot_leave_here지금 자리를 못 비움연구자 설정
3asked_too_often오늘 부탁을 너무 많이 받음연구자 설정 (helperContactCap)
4too_far너무 멀어서연구자 설정, 거리는 도로망에서 계산
  • 수락 확률은 넣지 않는다(D077). 변이는 이미 하루 실현에서 seed로 들어온다. 결정에까지 주사위를 넣으면 근거 없는 변이를 두 번 만든다.
  • 이웃 우선 정책(D078): 한 명만 묻고 끝나면 "이장 대신 다른 한 명"일 뿐이라, 거절하면 다음 사람에게 neighbourAskLimit까지 묻는다. 몇 명의 하루를 건드렸는지가 곧 결과다.
  • 거절은 신뢰 하락으로 계산하지 않는다.

5. 머리와 주민 — 두 층의 모델 D082–D085

연구자 지시: "MEDial은 AI Care Orchestrator라 LLM이 컨텍스트를 최대한 이해해야 하고, 후보 고르는 것도 상황을 다 꿰고 있는 LLM이 해야 한다." 주민은 "LLM이 전부 정하고 표는 기록만".

D082

울타리 — 노브는 고른 뒤에 검사한다

머리가 후보·순서를 고르면 코드가 설계자 조건을 검사한다.

  • 전원을 후보표에 적었나 · 본인에게 부탁하지 않았나
  • 이장은 allowHeadContact일 때만 · 인원은 neighbourAskLimit 이하
  • head_first → 첫 사람이 이장 · retry_then_clinic → 이웃 금지
  • relation_first → 기록된 관계만, 이장은 마지막 D087
  • wait는 5~120분, 한 건에 두 번까지 D084
어기면 문제 목록을 붙여 한 번 다시 묻고, 두 번째도 어기면 adapter_error. 규칙 정책 답으로 대체하지 않는다.
D083

주민 — LLM이 정하고, 표는 옆에 적기만

같은 view로 거절 표가 냈을 답을 ruleTableSaid · agreesWithRuleTable로 사건 옆에 남긴다.

  • 거절 사건의 rule은 llm_judgement, reason은 본인 말
  • 넘김(relay)은 기록된 관계 안에서만 — 엔진이 다시 검증
  • "어디 있을지"는 장소 단위 지식이 있는 사람에게만 묻는다
화면 표와 어긋난 답에 규칙표라면 수락 태그. 표를 앞에 세우면 LLM 주민이 아니라 표에 말을 입힌 것이 된다.
D084

wait는 시계가 달린 결정

실제 flash-lite 머리가 첫 판단에서 "40분 기다린다"를 골랐는데 깨우는 장치가 없어 하루가 그대로 끝났다.

고침 waitMinutes 뒤 같은 질문이 돌아온다(medial.waiting reason=head_wait untilMs). 세 번째 wait은 실패.
D085

두 층의 모델

머리는 상황 전체를 읽고 후보를 고르는 한 번의 무거운 판단, 주민은 하루 열두 번의 가벼운 한 답.

기록 ModelPolicy에 headModelId·residentModelId가 따로 있고 attempt 입력 해시에 들어간다. 머리 모델을 바꿔도 주민 기록은 그대로 재생된다.

6. 기록·재생과 공급자

  • 잘 부탁하는 대신 받아 적고 재생한다. temperature=0도 결정론이 아니다. 호출 키는 모델 · 온도 · 프롬프트 판 · 행위자 · 몇 번째 호출 · 프롬프트 본문의 내용 주소이고, 벽시계는 뺐다.
  • 재생 모드에서 기록이 없는 프롬프트는 MissingModelCall로 실패한다. 조용히 다시 부르면 재생처럼 보이면서 결과가 달라진다.
  • 분기(fork)는 체크포인트 앞의 머리·주민 호출을 모두 재생한다.
  • 프롬프트 판: prompt-v2(두 층) → v3(재연락은 코드, schedule_contact 선택지 제거) → v4(no_lead 단계).
공급자는 Gemini 하나 (2026-09-15, 연구자 지시). OpenAI·Anthropic 경로와 MEDIAL_LLM_PROVIDER를 걷어냈다. "괜히 헷갈린다. 필요하면 그때 새로 추가." 키는 GOOGLE_API_KEY 하나, OpenAI 호환 엔드포인트 + json_schema. 키는 서버 환경변수에서만 읽고 기록·로그·문서에 넣지 않는다. 같은 날 키를 교체했고 60회 이상 호출에 429가 없어 유료 등급으로 판단했다.

7. 재연락 — 모든 연락 순서의 첫 단계 D086

재연락은 어르신이 응답하지 않을 때, 이웃이나 보건소를 부르기 전에 본인에게 시간을 두고 다시 연락해 보는 것이다. retryCount(몇 번) · retryIntervalMin(몇 분 간격) · quietWindowMin(최소 간격)으로 정한다.

드러난 경위

⚠ 실행되지 않는 변경이 "통과"로 확정됐다. 실제 모델로 반복 루프를 돌리자, 1세대 개선안 "이웃 요청 전 1회 재호출"(retryCount 0→1)이 기계 검증을 통과해 확정됐는데 2세대 로그가 부모와 한 글자도 다르지 않았다. 재연락이 retry_then_clinic에서만 실행됐기 때문이다. 규칙 머리로 돌려도 똑같았다. 비교 화면은 "정책만 다르게 실행했다, 차이 0"을 보여 주었고, 디자이너는 "재연락은 효과가 없다"고 읽게 되어 있었다.

연구자와 정한 것

  • 순서는 재연락 → 가까운 관계 → 이장. 단, 이것은 고정 규칙이 아니라 비교할 정책 하나로 둔다(8장).
  • 재연락 자체는 설계 선택이 아니라 엔진 버그 수정이다: 노브 하나가 모든 정책에서 같은 뜻을 가져야 한다.

로직

MedialPolicy._retry_due(ctx)                   # 규칙 머리 · 모델 머리 공통
  if ctx.attempt_number > retryCount: return None
  at = max(now + retryIntervalMin, lastContact + quietWindowMin)
  → schedule_contact(subject, at, channel=phone, attemptNumber+1)

on_unanswered_checkin:  인계 기한 → 재연락 → 연락 순서
engine._on_missed:      retry_then_clinic 이고 재연락이 남지 않았으면 → on_retry_exhausted(보건소)
  • 두 번째부터는 전화. 안내 시계는 집에서만 닿으므로, 같은 기기로 다시 거는 것은 새 정보를 주지 않는다.
  • 모델 머리의 decide는 재연락이 끝난 뒤에만 불리고, policy.retriesAlreadyMade로 그 사실을 안다.

예: 정책 B(재연락 2회, 40분) — 연구자 기록

시각MEDial이 한 것결과세계의 이유 (연구자만)

재연락이 맞바꾸는 것: 잠깐 자리를 비운 경우라면 이웃의 시간을 한 번도 쓰지 않고 풀린다. 정말 문제가 생긴 경우라면 확인이 늦어진다. "누구의 시간으로"의 질문에서 이웃의 시간 ↔ 확인까지 걸리는 시간을 맞바꾸는 노브다.

"가까운 관계"는 무엇으로 정하나 — 기록된 것만

제안은 "바로 옆집이거나 자주 만나는 사람"이었다. 둘을 나눠서 봤다.

  • 옆집(거리)은 지도에서 계산할 수 있지만, 가깝게 산다고 가까운 사이는 아니다. 거리 기준은 이미 정책 C다.
  • 자주 만나는 사람(관계)은 relations.py의 기록된 관계만 쓴다. 관계를 추가하는 Change Set은 허용하지 않는다 — 외로운 사람에게 친구를 만들어 주는 것은 MEDial의 개선이 아니라 사례를 지우는 것이다.

12. 발견과 해석

발견 1

P1에게는 어떤 순서를 짜도 이장에게 간다

D는 A와 같은 사람(이장)에게 간다. P1의 기록된 관계가 이장 하나뿐이기 때문이다. 달라진 것은 40분 늦은 확인과, 그 사이 P1이 더 멀리 가 있어 이장의 수고가 4.2분 늘어난 것(18.8 → 23.0분).

해석 이 사례에서 "누구의 시간으로"의 답은 연락 순서가 아니라 P1의 관계가 이장 하나에 걸려 있다는 기록이 정한다. 재연락이 이웃의 시간을 아끼려면 본인이 두 번째 전화를 받아야 하는데, 이 하루의 P1은 밭에 있어 받지 않는다.
발견 2

이장에게 몰리지 않게 하려던 C도 이장의 지식으로 끝난다

C는 이제 해결되지만, 이장 한 사람의 18.8분이 두 사람의 22.2분으로 나뉘었고 규칙 머리는 거절할 사람 둘에게도 물었다.

해석 이장의 걷는 시간은 줄일 수 있어도, 이장의 아는 것은 대체되지 않았다. 부담의 종류가 이동 노동에서 정보 제공으로 옮겨 갔을 뿐이다.
발견 3

모델 머리는 거절을 만들지 않았다

C에서 모델 머리는 가게를 비울 수 없는 P10·P11을 건너뛰고 P9에게 먼저 갔다(규칙 머리는 둘에게 물어 거절 두 번). 연락한 사람 4명 → 2명.

주의 합성 마을 한 하루, 모델 머리 3~5회 반복이다. 흔들림을 본 것은 아니고, "모델 머리가 낫다"는 일반화는 할 수 없다.
방법론

실제 모델로 돌려야 드러나는 구멍이 있었다

가짜 모델 테스트 16건이 모두 통과한 상태에서, 실제 실행이 네 가지를 드러냈다: 깨우지 않는 wait, 모르는 사람에게 던진 질문, 실행되지 않는 재연락, 빈집에서 닫히는 요청.

적용 새 로직마다 실제 모델 반복 실행과 Playwright 캡처 확인을 짝으로 둔다.

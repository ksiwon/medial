## 2026-09-10 · v0.2 (첫 세로 흐름 구현)

| ID | 결정 | 이유·대안 | 확인 |
|---|---|---|---|

| D015 | 사건 deck은 "문진 발송"만 고정하고 응답 여부는 엔진이 계산 | deck이 `contact.no_response` 를 단정하면 다른 시각에 연락해도 결과가 같아져 정책 비교가 무의미해진다 | 정책 B의 12:15 통화가 P1의 기본 일과(12:02 귀가) 때문에 닿는 것을 테스트로 고정 |
| D016 | 장소별 연락 도달 여부를 표로 두고 각 항목에 provenance를 붙임 | 밭 미응답만 원본 사건에서 온 것이고 나머지는 연구자 가정이다. 하나의 확률값으로 뭉치면 근거의 차이가 사라진다 | 모든 무응답 사건이 `reachabilityBasis` 를 payload에 싣는다 |
| D017 | MEDial이 아는 일과는 baseline(공개 동의된 평소 일과)이며 realized가 아님 | 실시간 위치를 주면 시뮬레이션이 무의미해진다. 그러나 아무 일정도 모르면 후보 필터가 성립하지 않는다 | 이장 보고 전까지 MEDial 관측에 `FARM` 이 없음을 테스트로 확인 |
| D018 | 이장의 지역 지식은 그의 관측이며 MEDial은 보고를 통해서만 획득 | 이장을 MEDial의 하위 실행자로 두지 않는다는 03 문서의 요구를 구조로 구현 | 획득한 관측의 confidence가 `reported` 로 저장됨 |
| D019 | 기관 담당자가 방문 대신 귀가 시각에 맞춰 통화하도록 규칙화 | 인계 시 공개 동의된 일과가 함께 넘어가므로 그것을 쓰는 것이 자연스럽고, 동시에 "공개량이 늘어난다"는 비용이 드러난다 | 정책 B의 공개 항목이 3개, 정책 A는 1개로 비교 화면에 나타남 |
| D020 | 실행은 attempt 생성 시 1회 계산하고 재생 커서만 서버에 기록 | 규칙 어댑터는 결정적이고 하루가 밀리초에 끝난다. 대안(실시간 진행)은 복잡도만 늘리고 "재생이 모델을 다시 부르지 않는다"는 요구를 지키기 어렵다 | seek/step/play 후 로그 fingerprint 불변 테스트 |
| D021 | 지도 애니메이션용 timeline을 실행 결과에서 만들어 함께 저장 | 지도·추적·지표가 각각 계산되면 어긋날 수 있다. 같은 실행에서 파생시키면 어긋날 수 없다 | 스냅샷과 사건 로그 일치 테스트 |
| D022 | Pydantic을 계약의 단일 원천으로 삼고 JSON Schema는 호환 대상으로 유지 | 06 문서의 방침. 사건별 payload 필수 키와 world-truth 가시성을 모델 검증으로 강제 | 생성 사건이 기존 domain.schema.json 검증을 통과 |
| D023 | 신규 도메인을 별도 서버(sim_main.py)와 별도 번들 청크로 분리 | 기존 서버는 Whisper·FAISS·트리아지를 로드한다. 연구 도구가 그것에 의존하면 API 키 없이 못 돌린다 | 빌드에서 SimulationApp/App 청크 분리 확인. `/api/sim/health` 가 `modelCalls: none` |
| D024 | 원자료 없이도 합성 마을로 실행되게 하고 화면에 출처 배지를 상시 표시 | 테스트·첫 실행이 git 제외된 원자료에 의존하면 안 되고, 합성 지형이 실제처럼 보이면 더 위험하다 | 27개 테스트 전부 합성 픽스처 사용. 상단 배지로 구분 |

## 2026-09-10 · v0.2.1 (남긴 데이터 이슈 해결)

| ID | 결정 | 이유·대안 | 확인 |
|---|---|---|---|
| D025 | 방위를 서술하지 않고 **측정해서 기록**한다. 그 결과로 분석 문서의 "동서 1.11 km"를 "남북"으로 정정했다 | 대안은 코드에서 방위를 계속 회피하는 것이었으나, 그러면 오기가 문서에 남아 논문까지 간다. 측정값(P9→미가식당 5.3°, 동서 381 m·남북 1153 m)이 원본 시뮬레이터 산문("남쪽 끝", "읍내는 북쪽")과 일치하므로 오류는 후속 분석 문서 두 곳에 한정된다. 거리 값과 논증은 방위와 무관해 그대로 두었다 | `geometry.orientationChecks` · 남북/동서 폭과 방위각 테스트 · 원자료 있을 때 1111 m·바다 동쪽·읍내 북쪽 확인 |
| D026 | 도로망 간선 출처를 **import 시점에 강제 검증**한다 | "병합이 없는 도로를 만든 것 아닌가"를 추측으로 남기지 않는다. 검사 결과 간선 350개 중 원본에 없는 것 0개였고, 짧은 경로는 다른 원본 경로 구간을 공유 정점에서 이은 실제 도로였다. 대안(허용 오차로 스냅)은 없는 교차로를 만들 수 있어 채택하지 않았다 | `roadGraphProvenance.allEdgesFromSourcePolylines` · 위반 시 import 실패 · 테스트에서 독립 재계산 |
| D027 | 구간 거리를 하나로 합치지 않고 `sourceM`/`graphM` 둘 다 보관하고, 사건 payload가 어느 쪽인지 밝힌다 | 둘 다 맞는 값이고 뜻이 다르다(원본이 고른 경로 vs 전체 도로망 최단 경로). 평균이나 택일은 근거를 지운다. `distanceBasis` 를 로그에 실어 읽는 사람이 헷갈릴 수 없게 했다 | `namedRouteDistances` 74구간 · `graphM > sourceM` 이면 import 실패 · travel 사건의 `distanceBasis` 테스트 |
| D028 | 데이터 이슈에 `open`/`resolved` 상태를 두고 화면에 노출한다 | 해결된 것과 남은 것이 같은 목록에 섞여 있으면 "기록했다"가 "처리했다"처럼 읽힌다 | 지도 하단 데이터 이슈 패널 · 상태 필드 테스트 |
| D029 | 지도 timeline과 결정 trace를 실행 결과와 함께 SQLite에 저장한다 | 메모리에만 두었더니 서버를 다시 켠 뒤 지난 시도를 열면 지도가 비었다. 실행의 일부이지 캐시가 아니다. 구버전 DB는 ALTER로 이관한다 | 새 프로세스에서 같은 DB를 열어 timeline·trace·metrics 동일 확인, 스냅샷·비교 동작 확인 |
| D030 | registry에 schemaVersion을 두고 구버전이면 재생성 명령과 함께 거부한다 | 구버전 registry는 화면 한참 뒤에서 정의되지 않은 값으로 터진다. 원인 자리에서 실패시키는 편이 낫다 | `village/2` 미만 또는 필수 블록 누락 시 StaleRegistryError |

## 2026-09-10 · v0.2 (검토 R01~R08 대응, 페르소나·T004, 화면)

| ID | 결정 | 이유·대안 | 확인 |
|---|---|---|---|
| D031 | 시도 ID를 UUID로 바꾸고 저장을 **삽입 전용**으로 한다. 충돌은 덮어쓰지 않고 실패시킨다 | 프로세스 내 카운터가 재시작마다 1로 돌아가고 `INSERT OR REPLACE` 가 어제 기록을 조용히 다시 썼다. 조용히 바뀌는 연구 기록은 없는 기록보다 나쁘다. 대안(기존 DB 삭제)은 계보를 버리므로 채택하지 않았다 | 재시작 후 동일 정책 생성·fork에서 이전 시도 불변 · 중복 ID 시 부분 잔존 없음 · 구버전 행은 읽을 때 `lineage: root` 로 보정만 하고 다시 쓰지 않음 |

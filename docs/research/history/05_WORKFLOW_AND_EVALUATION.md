# 05. 이 디자인 툴을 사용하는 방법과 평가

## 1. 한 연구 세션의 흐름

예시 소요 60~90분은 진행 설계안이며 연구 결과가 아니다.

1. Core item을 문장으로 적는다. 예: “원래 외출하는 주민의 일정에 의료 이동 지원을 얹는다.”
2. 해결하려는 필요와 아직 모르는 것을 쓴다. 목표를 “만족도 최대화” 한 줄로 줄이지 않는다.
3. 고정할 조건을 정한다: 페르소나·기본 일과·사건 deck·자원·기간.
4. MEDial의 역할/관측/정책을 선택하고 실행 A를 만든다.
5. 결정 시점에서 멈춘다. MEDial이 알았던 것, 후보와 제외 이유, 당사자의 반응, 일정 변경을 확인한다.
6. 주민/이장/담당자 관점으로 장면을 다시 본다. 필요하면 snapshot 대화를 연다.
7. 관찰 카드를 작성한다: 장면 → 불확실한 가정 → 가능한 설명 → 수정할 조건 → 예상 손실.
8. A를 보존하고 B로 분기한다. 바꾼 필드와 이유를 기록한다.
9. 동일한 외생 사건을 넣어 A/B를 비교한다. 예상과 다른 결과도 버리지 않는다.
10. 주요 장면과 논쟁점을 추려 당사자·기관 담당자에게 확인할 질문으로 내보낸다.

도구가 새 아이디어 문장을 실행 규칙으로 자동 번역할 경우, 컴파일한 정책·가정·지원하지 않는 요구를 먼저 보여준다. 문장을 입력했는데 실제로는 아무 조건도 안 바뀌는 상태를 숨기지 않는다.

## 2. 화면 구성의 기준

왼쪽 평면 지도:
- 사실적 지리와 실제 이동을 표시. 사람/차량의 위치는 엔진 상태 한 곳에서 받음.
- 함께 있음은 실제 위치 또는 같은 차량/상호작용 세션으로 묶음. 사회적 관계와 혼동하지 않음.
- 작은 그룹 팝업: 주민 선택 → 현재 행동 → 더 알아보기.
- 마을 밖 주민과 기관은 별도 목록. 추정 위치에는 추정 표시.
- 연구자 전체보기와 MEDial이 아는 정보 보기 전환. 이를 가장 중요한 연구용 보기 기능으로 둔다.

오른쪽 위:
- 선택한 core item·attempt·policy revision.
- MEDial 상태: 관측/추가확인/제안/응답대기/자원대기/수행/기관인계.
- 후보/제외 이유/공개 범위/다음 사건. 결정 이유의 한 문장과 근거 링크.
- 접수/연락/수락/수행/완료를 별도 수치로 표시.

오른쪽 아래:
- 대화, 사건, 이슈, 기관 회신을 시간순 통합.
- 사건 클릭 → 연결된 일정·의사결정·결과.
- 메시지의 발신자·수신자·관측시각·공개범위.
- 주민 상세: 원래 일과와 바뀐 일과, 사용 기회·요청·거절, 사건별 평가.
- 보건소 상세: 소장 운영 조건과 담당자 큐를 구분.
- 119 상세: 상황실·출동대·인계 상태를 구분.

시도 비교:
- 트리: 부모→조건 변화→새 실행.
- 같은 사건의 대응 장면을 나란히 재생.
- 여러 지표와 주민별 분포, 지표 분모, 미해결/확인불가를 표시.
- 모델 출력·연구자 해석·실제 사람 정정을 서로 다른 출처로 표시.
- 평균 점수로 자동 우승자를 고르지 않음.

## 3. 만족도는 세 층으로 본다

### A. 실행 로그에서 계산하는 결과

| 지표 | 정의 | 해석 |
|---|---|---|
| 필요 관측률 | 시스템이 알게 된 필요 / 평가용 생성 필요 | WorldTruth 기준, 연구자 전용; 실제 필요 포착률 아님 |
| 요청 전환 | 자발 요청 / 표현 가능한 필요 기회 | 도구 사용 유도 정책에 따라 분모가 바뀌면 별도 비교 |
| 연락 도달률 | 수신 확인된 연락 / 발신 시도 | 전송·수신·응답을 구분 |
| 수락률 | 수락 / 제안에 대해 판단 가능한 응답 | 무응답을 거절로 합치지 않음 |
| 기한 내 수행 | 확인된 수행 / 수행이 필요한 유효 요청 | 연락만 성공한 건 제외 |
| 미해결 | 유효 요청 중 종료 시 수행/인계 미완료 | 취소·철회·기관대기 등 이유별 |
| 대기시간 | 요청→서비스 시작, 요청→완료/인계 | 미완료는 censored. 성공한 요청 평균만 단독 표기 금지 |
| 추가 부담 | 실현된 행동시간−같은 기본 계획의 해당 시간; 추가 거리·중단 횟수 | 수혜자·도우미·이장·직원 각각 |
| 공개량 | event별 고유 수신자×민감 필드 수; 비허용 공개 건수 별도 | 단순 인원 합계를 프라이버시 점수로 취급하지 않음 |
| 역할 경계 위반 | 권한 없는 행동의 제안/실행 건수 | 제안 차단도 실패 후보로 기록 |
| 기관 업무 | 검토·연락·방문·수습 시간, 대기열 최대/시간평균 | 인계는 업무 이전이므로 받는 쪽 비용 포함 |
| 사용 빈도 | 주민별 자발 요청, 확인 응답, 알림 수신, 도움 수행을 분리 | 사용 많음=만족 아님; 요청 사건을 많이 넣은 결과일 수 있음 |

12명 각각의 분포와 접촉이 적은 사람을 본다. 평균/최대 부담과 함께 역할별 부하를 비교한다. Gini 같은 불균등 지표는 전체 부담이 0이면 N/A; 응급의 불균등이 무조건 나쁘다는 해석도 하지 않는다.

### B. 에이전트가 남기는 경험 평가

이름: '시뮬레이션 경험 평가'. 사람의 만족도나 예측 정확도라는 이름을 쓰지 않는다.

평가 단위: 본인이 받은 연락·제안·공개·수행 경험. 하루 전체 정답을 보고 평가하지 않는다.

기본 항목:
- 일이 해결되었는가/다음 담당자가 명확한가
- 내 일정과 노동이 존중되었는가
- 거절·시간 제안·공개 범위 선택이 가능했는가
- 설명을 이해했고 필요한 것을 알 수 있었는가
- 민감한 정보가 원하지 않는 상대에게 전달되었는가
- 다음에 같은 방식으로 부탁받거나 사용할 의향이 있는가

각 항목: 긍정/혼합/부정/판단불가 + 이유 + observedEventIds + evidenceIds.
숫자가 필요하면 1~5 ordinal을 부가하되 unknown을 허용하고 평균의 의미를 제한한다. 원본의 'AI 신뢰도'나 현재 데모의 고정 별점은 사용하지 않는다.

수혜자와 도움 제공자의 평가를 별도로 묻는다. 일이 해결되어 고마워하면서 다음번엔 돕기 어렵다는 응답도 가능하다. 경험이 없으면 만족도는 unknown; 시스템 비사용 이유만 별도 기록한다.

자동 평가자가 특정 발언의 근거·일관성·정보 권한을 검사할 수는 있다. 그러나 같은 LLM이 주민을 연기하고 자기 정책을 채점한 점수를 인간 근거처럼 사용하면 안 된다. 독립 프롬프트/검토자는 보조책이며 인간 검토를 대체하지 않는다.

### C. 실제 당사자·기관 담당자의 검토

- “이 장면에서 본인이라면 이렇게 말하거나 행동할까요?”
- “그렇게 하지 못하게 하는 사정이 빠졌나요?”
- “어느 단계에서 누구에게 결정권이 있어야 하나요?”
- “A와 B 중 어떤 방식이 더 받아들일 만하며 왜인가요?”
- “본인 입장은 맞지만 이웃/기관 입장이 틀리게 표현되었나요?”

부합·수정 필요·부적절·판단불가를 구분하고 원문 의견을 보존한다. 재방문은 마지막 합격 절차만으로 두지 말고, 가능하면 중간 핵심 가정에 대해서도 짧게 확인한다. 실제 참여 일정·규모는 접근성과 연구 승인 범위에 맞춰 정한다.

## 4. 비교 실험과 반복 개발을 구분한다

- 탐색 반복: 목표·core item·기관 역할까지 바꿀 수 있음. 발견의 계보가 목적.
- 통제 비교: 바꾼 조건을 좁히고 동일 초기 상태·외생 사건·가정으로 실행. 가능한 한 한 종류의 정책 변경부터.
- 장기 실행: 한 실행 안에서 기억/부담이 누적. 정책 revision은 고정.
- 정책 학습 비교: 업데이트 알고리즘을 실험하려면 별도의 training/development/held-out 시나리오 분할.

두 실행의 random seed 숫자 하나만 같다고 동일 조건이 아니다. 호출 수가 달라져 난수열이 밀리지 않도록 사건ID·actor·기제별로 난수 stream을 키잉한다. 외생 deck은 실행 전에 생성·동결하고, 정책으로 발생한 내생 사건은 달라도 된다.

동일 seed·temperature는 LLM의 재현성을 보장하지 않는다. 완전한 재생은 저장한 응답과 committed event log로 한다. 새 모델 호출 재실행은 replicate로 기록한다.

초기 계획:
- 동일 한 사건의 2~3가지 정책으로 세로 흐름 확인.
- 작동한 후 고정 사건 묶음×초기 3개 seed로 debugging.
- 비교 후보에 대해 최소 5개 독립 LLM 재실행부터 불안정성 탐색, 추가 여부는 분산·비용·질문에 따라 결정.
- 이 숫자는 유의성 확보 근거가 아니다. 주장은 모델 안의 차이와 설계 발견으로 제한.

## 5. 디자인 툴 자체의 연구 평가

MEDial 성능과 툴의 연구 기여는 다른 평가다.

제안 연구:
- 연구자 스스로 3개 core item에 대해 여러 시도를 남기는 longitudinal design log.
- 디자이너/연구자가 정적 페르소나·시나리오 문서와 이 툴을 사용하는 비교 세션.
- 조건 순서를 교차하고 주제를 바꿔 학습 효과를 줄임.
- 참가자 수는 초기 4~6명 파일럿부터 사용성·프로토콜을 확인하고 후속 규모를 결정. 통계 검정력을 보장하는 수치가 아님.
- 자료: 생각 말하기, 화면 기록, 시도 변경 내역, 근거 검토, 최종 설명, 실제 이해관계자 피드백.

측정할 것:
- 새 아이디어 수만 아니라 실제로 서로 다른 설계 대안인지.
- 발견한 가정·트레이드오프·권한 충돌의 구체성.
- 변경 이유가 어떤 사건·근거에서 나왔는지 추적 가능성.
- 다음 현장 질문의 유용성·확인 가능성.
- 합성 결과에 대한 과신/의인화, 근거 없는 정책 채택.
- 기관/주민 검토 후 유지·수정·폐기된 설계의 이유.

정성 코딩에서 독립 검토와 이견 조정을 남긴다. '툴을 좋아했다'만으로 설계의 질이 높아졌다고 주장하지 않는다.

## 6. 중단과 채택 기준

불만이 0이 되면 멈추는 루프를 만들지 않는다.
- 핵심 기관 권한·시간·정보 오류는 수정 전 결과 채택 불가.
- 설명 못 하는 승패는 원인 분석으로 돌아간다.
- 예산 내 새로운 발견이 줄고, 미사용 사건에서도 핵심 제약을 지키고, 남은 가정이 정리되면 현장 검토로 넘어간다.
- 인간의 반박은 점수 평균으로 상쇄하지 않고 새로운 근거/정책 revision의 출발점으로 남긴다.

# Resident Agents as Evaluators 리팩터링 검토와 구현 지시서

작성일: 2026-09-15

이 문서는 연구 초점, 다른 서비스로의 이전 가능성, 정책·서비스 디자이너 UX, 선행 연구, 코드 구조를 함께 검토한 리팩터링 제안이다. 현재 코드를 수정한 결과 보고서가 아니다. 실제 구현을 맡을 LLM은 27번 실행 프롬프트와 함께 읽는다.

## 1. 판단의 기준과 검토 범위

최우선 기준은 `19_RESIDENT_AGENTS_AS_EVALUATORS.md`, 20~23번 확정 계약, `RESEARCH_NOTE_2026-09-15.html` 1장이다. 최신 연구노트 본문, 25번 채록 가이드, DEVELOPMENT의 관련 구현·한계, 실제 프런트와 서버의 주요 실행 경로를 읽었다. URP 폴더의 과거 `URP_연구노트_박정원_MEDial.docx`에서 목표 관련 문단도 확인했다. 과거 문서는 VUI 의료상담과 RAG를 중심으로 하므로 현재 연구의 구현 요구로 사용하지 않는다. 모든 과거 PDF·인터뷰 전사를 대조한 것은 아니다.

코드 검토는 `engine.py`, `runner.py`, `relations.py`, `ledger.py`, `persona.py`, iteration의 계약·검증·서비스·평가 근거·종합, SimulationApp·PrepareScreen·ObserveScreen·CompareScreen·PersonPanel·FieldSheet·스토어와 테스트 구성에 집중했다. 아래 줄 번호는 작성 시점 기준이며 구현자는 심볼로 재확인한다.

브라우저 연결은 런타임 종료 오류로 두 번 실패했고, 기존 스크린샷 열기도 샌드박스 프로세스 오류로 실패했다. 따라서 화면에 관한 판단은 **코드 기반 전문가 검토**이며 실제 화면 조작이나 정책 디자이너 사용성 실험 결과가 아니다. 이번 작업에서 전체 테스트와 실제 모델 호출을 재실행하지 않았다. 노트에 있는 실행 수치도 독립 재현값으로 보고하지 않는다.

### 연구가 최종적으로 보여야 할 것

인터뷰에 근거한 주민 에이전트가 자신이 경험한 사건으로 서비스를 평가하고, 그 평가가 사람이 확인한 운영 규칙 수정으로 연결되며, 같은 조건의 재실행과 실제 주민 검토를 통해 **어디에서 유용하고 어디에서 실패하는지** 드러나는 디자인 방법.

논문과 제품이 공통으로 내야 할 최소 산출물은 다음 한 묶음이다.

1. 서비스 경험 장면과 당시 행위자에게 보였던 정보.
2. 주민별 평가 항목, 사건 근거, 인터뷰 근거, 판단 불가.
3. 그 평가에서 출발한 변경 전후 운영 규칙과 연구자 판단 이유.
4. 같은 조건의 재실행에서 바뀐 사건·부담·평가와 바뀌지 않은 것.
5. 가정 의존, 평가·종합 오류, 미경험, 자료 부족을 포함한 사용 한계.
6. 실제 주민에게 확인할 질문과 이후 일치·정정·충돌 기록.

정책별 성능 순위와 마을 애니메이션은 이 산출물의 근거를 이해하는 데 필요한 범위로 둔다. 규칙표와 모델의 불일치는 실제 주민과의 불일치가 아니다. 기존 82문항은 모델이 놓인 조건의 편향을 드러내는 감사 자료이며 주민 대표성이나 서비스 효과의 검증 결과로 확대하지 않는다. 종합 오류의 AI 초안 라벨도 사람 판정 정확도로 표현하지 않는다.

## 2. 핵심 진단

### F01 P0 설명과 실행의 진실이 둘이다

근거: `CompareScreen.tsx:922` 이후 편집 UI 및 `makeEditor`/`editorPayload`, `iteration/service.py:_save_researcher_change_set`, `iteration/validation.py:change_set_to_policy_changes`.

편집자는 afterRule 문장과 내부 executionBindings 값을 따로 바꾼다. 서버는 실행값의 타입·현재값·지원 여부를 검사하지만 문장이 그 값과 같은 의미인지는 검사하지 않는다. 예를 들어 유효 초안의 실행값은 재연락 1회인데 문장을 2회로 바꿔도 실행에는 binding의 1회가 쓰인다. 기존 초안의 변경 전 값과 달라야 한다는 검사만으로 이 불일치를 막지 못한다.

이것은 단순한 용어 문제가 아니라 평가→수정의 추적 가능성을 훼손하는 구조다. 자유 설명은 의도와 이유로만 저장하고, 실행 규칙·요약 문장·diff·binding을 하나의 구조화된 의미 규칙에서 생성해야 한다. LLM에게 두 표현의 일치를 판정시키는 추가 계층으로 해결하지 않는다.

### F02 P1 주민 평가가 제품의 중심으로 드러나지 않는다

근거: `SimulationApp.tsx:NAV`의 실험 준비/마을 관찰/결과 비교, `ObserveScreen.tsx`의 3열 배치, `PersonPanel.tsx:354,409`의 회고 토글과 하루 종료 평가.

주민을 찾아 상세와 회고를 열어야 평가를 읽는 경로는 경험 이해에는 유용하지만 전체 평가를 검토하기에는 단계가 많다. 19번 문서의 Resident Evaluations 중심 구조가 라우트 수준에 구현되어 있지 않다. 평가 검토를 재생 커서와 분리하고, 평가에서 해당 시점 장면을 여는 경로를 둔다. 관찰 중 미래 평가를 현재 관측처럼 보여 주지 않는 기존 경계는 유지한다.

### F03 P1 새 가설도 기존 유효 초안에 종속된다

근거: `iteration/service.py:342` 부근의 templateChangeSetId 필수 조회와 valid 검사, `CompareScreen.tsx`의 drafts.length 조건 안에 있는 새 연구자 가설 버튼.

유효 AI/규칙 초안이 없으면 연구자가 지원되는 변경을 직접 작성하기도 어렵다. '새 가설'이 사실상 기존 초안의 복제다. 지원 규칙 카탈로그에서 새 변경을 만들 수 있어야 한다. 검증되지 않은 자유 Task 생성은 허용하지 않는다.

### F04 P1 공동체 자료가 엔진 코드 안에 있다

근거: `relations.py:27–79`의 P번호 동행군·사촌·동승·안부 관계 상수, `persona.py:40,91,288`의 파일명/P12 특례, `runner.py:75,158`의 기본 관계 로드, `story.ts:98`의 P6 이장 표시.

다른 공동체가 P번호를 재사용하면 은점 관계가 섞일 수 있고, 전혀 다른 ID를 쓰면 관계·표시·사례 설정을 여러 파일에서 고쳐야 한다. 데이터에 따른 결과와 구현자의 수작업이 뒤섞인다. ID, 인원, 역할, 관계, 근거 밀도는 CaseBundle의 자료로 이동한다. 합성 fixture가 같은 ID와 관계 구조를 쓰는 것만으로 이전 가능성이 증명되지는 않는다.

### F05 P1 채록 공백은 표시되지만 실행 입력 전체가 아직 자료화되지 않았다

근거: 25번 가이드 3~5장, `ledger.py:legacy_ledger`, `environment.py`, `agents/decline_rules.py`, 최신 노트 7·10장.

장부가 없으면 모두 not_asked지만 이장이 전원 일과를 안다는 가정을 만들어 기존 결과를 유지한다. 연락 조건·거절 조건의 실제 값은 장부의 상태만으로 결정되지 않는다. 신규 사례에서는 장부 없음에 숨은 역할 가정을 자동 생성하지 않는다. 부족한 자료와 명시적으로 승인된 가정으로만 실행하고, 해당 가정이 어떤 평가에 영향을 주는지 연결한다. 과거 실행은 당시 입력을 보존한다.

### F06 P1 구현되지 않은 서비스 변화와 효과가 없는 변화를 구별해야 한다

근거: `validation.py:SUPPORTED_QUESTS/SUPPORTED_TASKS/SUPPORTED_RULE_FIELDS`, 실행 변환 함수, 최신 노트 5.2·8.1.

의미 필드 이름이 넓더라도 현재 실행은 제한된 PolicyParams/contactStrategy binding을 바꾸는 방식이다. 완전한 Task 그래프 편집기로 읽히면 오해다. 변경이 해당 사례에서 지원되는지, 적용 조건이 실행 중 발생했는지, 실제 규칙 분기를 지났는지를 별도로 기록한다. 사건이 같다는 사실만으로 '정책 효과 없음'이나 '죽은 기능'을 판정하지 않는다.

### F07 P1 인간 검토의 비교 단위와 시점이 느슨하다

근거: `FieldSheet.tsx:348–428`. 공개 전/후를 사용자가 dropdown으로 선택하고, 일치 값은 unknown/agreement/partial/correction이다. 명시적인 disagreement 선택이 없으며, 응답자 역할과 장면 주체가 따로 식별되지 않고 actorId는 장면에서 가져온다. 공개 전 질문에서도 일치 판단 폼이 함께 보인다.

실제 주민 검토는 구현되어 있으나 연구 프로토콜을 온전히 강제하지 않는다. 본인·가족·연구자 메모를 섞지 않고, 먼저 독립 응답을 저장한 후 에이전트 평가를 공개하고 비교해야 한다. 한 장면 전체의 일치와 특정 평가 항목의 정정을 연결할 수 있어야 한다. 현장 연구를 지금 수행한다는 의미가 아니라 기록 도구를 준비하는 작업이다.

### F08 P1 종합의 근거 판정이 다시 검토 가능해야 한다

근거: 최신 노트 8.4, `iteration/synthesis.py`, `iteration/experience.py:validate_review`.

존재하는 사건 ID를 인용하는 것과 그 사건이 문장 주장을 뒷받침하는 것은 다르다. 현재 경험 validator의 자기 사건/근거 경계는 유용하므로 보존한다. 종합이 분류·제외한 주장에는 원본 ReviewItem을 연결하고, 없는 주장을 만들어 '걸러냈다'고 보고하지 못하게 한다. 기계적인 참조 검사와 사람이 해야 할 의미 판정을 구분한다.

### F09 P2 저장 실패 시 편집 맥락이 사라질 수 있다

근거: `CompareScreen.tsx`에서 onSaveResearcherChangeSet 호출 직후 setEditor(null), 상위 callback은 void 비동기 호출.

저장 성공을 기다리지 않고 편집기를 닫는다. 검증 오류가 나면 입력을 보존한 채 관련 필드 옆에 오류를 보여야 한다. boolean 자유 입력에서 true 이외 값을 false로 바꾸는 변환과 배열 입력의 JSON/쉼표 fallback도 타입별 컨트롤로 대체한다.

### F10 P2 구현 경로와 문서가 계속 겹쳐 쌓인다

근거: SimulationApp의 수동 A/B·Finding·PolicyEditor 경로, `DEVELOPMENT.md:84`의 온라인 호출 미실시 문장과 최신 노트 실제 실행 기록, DEVELOPMENT의 옛 ChangeProposal·자동 후보 시절 설명, 20번 문서의 제거된 selection.py 참조.

수동 비교를 남긴 이유인 '두 방법 비교'는 현재 RQ2의 로그/지표 대 평가+근거 비교와 같지 않다. 일반 UI에서 별도 정책 편집 경로를 유지하는 근거로 사용하지 않는다. 연구 조건은 동일 데이터의 읽기 전용 제공 방식 차이로 구현한다. 옛 실행 기록은 보존하되 신규 실행 경로는 하나로 통합한다. 현재 상태와 과거 이력을 문서에서 분리한다.

### F11 P2 큰 파일과 잦은 전체 상태 갱신은 변경 비용을 높인다

근거: engine.py 약 2천 물리 줄, CompareScreen.tsx 약 1.1천 줄, VillageMap.tsx 약 1천 줄. 정확한 줄 수 자체는 결함이 아니다. engine은 연락·전가·방문·기관·이동·관측을 한 클래스에 포함하고 CompareScreen은 비교 집계·변경 편집·확정·현장 진입을 모두 맡는다. `iterationStore.ts:283`은 detail과 generations를 순차 조회하고, SimulationApp은 두 스토어 전체를 구독한다.

성능 저하를 측정한 것은 아니다. 먼저 책임 분리와 상태 일관성을 개선하고, 폴링 응답량·렌더 횟수·스크롤 복구를 계측한다. 효과가 확인되지 않은 캐시·WebSocket·전면 상태관리 교체는 추가하지 않는다.

## 3. MEDial 외의 대상으로 일반화할 때의 난점

일반화를 세 단계로 구분한다. 이 구분 없이 모든 것을 설정 가능하게 만들면 연구의 초점과 구현 범위가 동시에 흐려진다.

| 수준 | 무엇이 바뀌는가 | 현재 가장 큰 장애물 | 이번 목표 |
|---|---|---|---|
| G1 다른 공동체 | 주민·관계·일과·장소·자료 공백 | 하드코딩 ID와 지역 가정, 수작업 자료 변환 | 데이터 교체만으로 검증 가능한 CaseBundle |
| G2 같은 공동체의 다른 서비스 | 접촉/경험 사건, 수정 가능한 규칙, 해결 기준 | MEDial Quest/Task·의료 사건·지표 결합 | 작은 ServiceAdapter 경계와 비의료 합성 검증 사례 |
| G3 다른 분야의 방법 재사용 | 평가 차원·기관·참여 프로토콜 | 의료 맥락의 평가·근거 체계가 타당한지 새 연구 필요 | 확장 절차와 한계 명시. 범용 제품은 만들지 않음 |

### 제3자가 부딪힐 실제 작업

1. 인터뷰를 어떻게 실행 가능한 입력으로 옮기는지 결정해야 한다. 채록 상태뿐 아니라 값, 근거 위치, 사실/해석/가정, 누가 관측 가능한지를 작성할 양식이 필요하다.
2. 같은 인터뷰를 다른 연구자가 코딩했을 때 관계·거절 조건이 달라질 수 있다. 코드 버전만 고정해서는 재현성이 확보되지 않는다. 근거 코딩과 변경 이력을 함께 보존해야 한다.
3. '병원 도착/안부 확인'을 다른 서비스의 완료로 치환해야 한다. 실행상 종료와 주민 필요 충족을 별도 필드로 유지해야 한다.
4. 서비스가 실제 외부 시스템인지, 정책 규칙 모형인지, LLM 조율자인지 구분해야 한다. ServiceAdapter로 연결했다고 외부 서비스의 성능을 검증한 것이 아니다. 실제 시스템 연결은 이번 범위 밖이다.
5. 서비스 평가 프롬프트와 서비스 개선 프롬프트가 같은 가정·모델에 의존하면 오류가 일관되게 재생산될 수 있다. 모델 교체만으로 해결하지 말고 독립된 근거 판정과 현장 검토를 둔다.
6. 주민 의사결정 오류, 서비스 오류, 평가 오류, 종합 오류를 구분해야 한다. 한 결과에 실패 종류와 발생 단계를 남긴다.
7. 같은 seed는 같은 외생 조건을 맞출 뿐 LLM 결과의 결정론을 보장하지 않는다. 동일 버전의 기록 재생, 모델 변이를 포함한 반복 실행, 서비스 변경 전후 비교를 명확히 구분한다.
8. 지역·사람·모델을 바꾸면 이전의 82문항 분모를 그대로 결과 옆에 표시할 수 없다. 감사 결과는 적용 가능한 입력·모델·프롬프트 조합에만 연결한다.

### 이전 가능성의 인수 조건

- P1~P12를 쓰지 않는 5인 합성 공동체, 이장 역할 없음, 관계 없음/미채록이 섞인 자료를 로드한다. 기존 관계·기관·별명이 자동 주입되지 않아야 한다.
- 비의료 사례는 '공동시설 이용 지원' 같은 한 가지 합성 서비스로 제한한다. 요청→안내/배정→지연/거절→이용 결과 정도의 제한된 사건과 규칙만 정의한다.
- 같은 평가·근거·수정·확정·비교 UI를 사용한다. 서비스별 복제 화면을 만들지 않는다.
- 새 사례를 추가할 때 공통 평가 엔진 파일에 서비스 이름 분기를 넣지 않아야 한다.
- 이 검증의 결론은 '소프트웨어 이전 가능성 확인'이다. 다른 주민 집단에서 방법의 타당성이 실증되었다고 쓰지 않는다.

### 연구 포지셔닝 제안

'LLM 주민이 피드백을 준다'만으로는 선행 연구와 겹친다. 제안하는 기여는 **지역 맥락에 놓인 개인의 근거 제한 평가를, 사람이 결정하는 운영 수정과 실제 주민 정정으로 연결하는 디자인 방법 및 그 실패 경계**다. 이 차별성이 유용한지는 RQ2와 RQ3로 입증해야 한다. 비슷한 시스템이 있다는 이유로 새 플랫폼 기능을 더하지 않는다.

## 5. 정책·서비스 디자이너의 목표 UX

### 기본 구조

전역 이름은 Resident Agents as Evaluators, 현재 평가 대상은 MEDial로 분리해서 표시한다. 기본 내비게이션은 다음 세 개만 둔다.

1. **사례와 서비스 경험** — 마을·자료 상태·사례·현재 운영 규칙, 실행과 핵심 장면.
2. **주민 평가** — 이번 실행에서 누구에게 어떤 도움·부담·모름이 생겼는지.
3. **개선과 확인** — 바꿀 규칙, 연구자 확인, 전후 변화, 현장 질문과 응답.

기본 작업은 '사례 하나 선택 → 실행 → 주민 평가 → 쟁점 선택 → 지원되는 규칙 수정 → 이유를 적고 재실행 → 변화와 현장 질문 확인'이다. 초기안과 수정안 한 쌍을 기본 단위로 하고 최대 3세대 설정을 첫 화면의 중심에서 없앤다. 추가 반복은 사용자가 현재 결과에서 명시적으로 시작한다.

### 화면별 요구사항

#### A 사례와 서비스 경험

- 기본 필수 선택은 사례와 초기 운영안 두 가지. 질문은 기본 문구를 제공하고 연구 질문임을 표시한다. 자연어 실행 명령처럼 보이지 않게 한다.
- 세계·관계·자원·근거 상태는 '이번 비교에서 고정되는 조건'으로 요약한다. 데이터 부족 자체를 전부 실행 금지로 만들지 않는다. 잘못된 참조/타입은 차단하고 불완전한 근거는 unknown 또는 명시적 가정으로 다룬다.
- 기본값은 기존처럼 모델 호출 없는 시연. 실제 모델 설정은 연구 설정에 두고 행동/평가/개선 역할별 실행 주체를 읽기 쉽게 보여 준다. 동승·기관의 규칙 실행을 모두 LLM인 것처럼 요약하지 않는다.
- 실행 버튼은 '이 조건으로 경험 생성'. 재생 버튼은 '기록 재생'. 두 상태와 진행 표시를 분리한다.
- 지도는 근거 장면을 설명하는 보조 영역. 사건 번호 슬라이더보다 '연락함/거절함/부탁이 넘어감/확인됨' 장면 이동을 우선한다. seq와 원시 payload는 감사 영역에 둔다.
- '전체 상황'과 '서비스가 알고 있는 정보'는 이름과 범위를 분명히 표시한다. 주민 평가 작성 컨텍스트에는 전체 상황 데이터를 주입하지 않는다.

#### B 주민 평가

- 실행 완료 후 기본 도착 화면. 주민 목록에서 경험 상태를 먼저 보여 주고, 선택하면 경험 요약→6개 평가 차원→요청한 변경→모름 순서로 읽는다.
- 평가 항목 한 개에서 사건 근거와 인터뷰 근거를 각각 한 번에 연다. 닫으면 같은 항목·필터·스크롤로 돌아온다.
- '미경험', '제안받고 거절', '응답하지 못함', '미해결'을 서로 다른 상태로 표시한다. 미경험을 부정 평가로 정렬하지 않는다.
- 쟁점 묶음은 원본 평가의 읽기용 요약이다. 소수 의견·반대 평가·종합 제외 항목을 탐색할 수 있게 한다. 부정 항목 수로 우선순위를 자동 결정하지 않는다.
- 카드에 '모의 주민 평가'를 명시하고, 원자료 기반 페르소나인지와 인간 응답인지 서로 다른 축으로 표시한다. 원자료 기반이어도 평가는 simulated다.
- 데이터 부족, 모델 조건 위반, 의미 근거 검토 필요는 관련 항목에 짧게 보이고 세부 감사는 펼쳐 본다.

#### C 개선과 확인

- 선택한 쟁점과 원본 평가를 상단에 고정. 관련된 운영 규칙만 편집한다. 예: '응답이 없으면 본인에게 [1]회, [20]분 간격으로 다시 연락한 뒤 [이웃에게 요청]'.
- 이 입력이 실제 실행값과 before/after 문장을 만든다. 기술적인 binding 입력란은 기본 편집 UI에서 제거한다.
- 자유문장 입력은 '이 변경을 시도하는 이유'이며 실행값을 대신하지 않는다. 실행할 수 없는 아이디어는 '현장 질문/후속 구현 제안'으로 저장한다.
- 초안 수정과 직접 작성을 모두 지원한다. 직접 작성은 supported rule catalog에서 시작하고 AI 초안 유무와 무관하게 가능하다.
- 초안을 여러 개 동시에 전부 펼치지 않는다. 선택한 한 안의 기대 효과·부담·영향받는 사람·다음에 볼 것을 보여 준다.
- 저장은 실행하지 않는다. 마지막 '이유를 기록하고 수정안 실행'만 실행 권한을 만든다. 버튼 인근에 해당 변경의 확정 이유를 둔다. 다른 안으로 바꾸면 이전 이유를 자동 재사용하지 않는다.
- '이번에는 수정하지 않음'을 명시적인 종료 경로로 둔다. 초안이 없거나 지지할 수 없어도 현장 질문을 만들 수 있어야 한다.
- 비교는 서비스 해결/미해결, 사람별 부담, 평가 변화, unknown, 가정 의존을 나란히 읽는다. 총점·승자·자동 채택 없음.
- '변경 규칙 적용됨/적용 상황이 없었음/실행 실패/비교 조건이 달라짐'을 구분한다. 차이 0만 보여 주지 않는다.

#### D 현장 확인은 개선 화면의 하위 흐름

- 장면 선택→공개 전 질문/응답→평가 공개→항목별 일치·정정·충돌·모름의 순서.
- 독립 응답을 저장하기 전에는 같은 참여자 화면에서 에이전트 평가를 숨긴다. 앱 밖에서 이미 공개되었을 수 있으므로 공개 이력은 기록이지 무편향 보증이 아니다.
- 응답자 pseudonymous ID, 역할, 평가 대상 주민 ID, 질문/장면/평가 항목 참조를 분리한다. 가족 의견은 본인의 응답으로 덮어쓰지 않는다.
- 정정 대상은 자료/세계 가정/주민 행동 모델/서비스 규칙/평가/종합 중 선택. 정정은 과거 실행을 변경하지 않고 후속 연구 입력으로 연결한다.
- 연구자 메모는 인간이 쓴 기록이지만 주민 검증 응답은 아니다. 출처와 역할 필터로 분리한다.

### 검증할 UX 가설과 목표

아래 수치는 달성 사실이 아니라 형성평가 목표다. 정책·서비스 디자이너 5~8명 정도로 먼저 문제를 발견하고 표본 규모는 실제 모집 여건에 맞춰 별도 확정한다.

- 준비된 사례에서 2분 안에 평가 대상·고정 조건·현재 운영안을 설명한다.
- 3분 안에 부담이 생긴 주민과 해당 사건/인터뷰 근거, unknown 하나를 찾는다.
- 원본 평가→변경 규칙→재실행을 설명할 수 있고 내부 JSON을 입력하지 않는다.
- '저장', '실행', '기록 재생', '현장 확인'의 효과를 혼동하지 않는다.
- 실험 세팅이 준비된 상태에서 평가 목록→근거 장면→원래 항목으로의 왕복은 각각 한 번의 명시적 동작으로 가능해야 한다.
- 사용자가 어느 안도 실행하지 않고 질문을 남겨 종료할 수 있다.
- 1440×900, 1366×768, 800px 폭과 키보드에서 가림·가로 넘침·이중 스크롤·focus 유실을 실제 브라우저로 확인한다.

## 6. 목표 아키텍처와 데이터 계약

구조 분리는 연구 책임의 경계에 맞춘다. 파일 수를 늘리는 것 자체가 목표는 아니다. 아래 이름은 제안이며 기존 계약과 의미가 같으면 재사용한다.

```text
CaseBundle (근거·주민·관계·일과·세계·시나리오)
     + ServiceAdapter (지원 규칙·서비스 의사결정)
     ↓
Simulation runtime (사건 순서·관측·자원·불변 로그)
     ↓
ActorExperience → ResidentEvaluation → IssueSynthesis
     ↓                        ↓ 원본 참조 보존
SemanticChange → validation → researcher confirmation
     ↓
ServiceRevision → rerun → Comparison → FieldReview
                     ↘ Failure/Boundary records
```

### C01 CaseBundle

필드: schemaVersion, caseId, version, sourceKind, residents, roleAssignments, places, routines, relationships, reachabilityRules, refusalConditions, elicitationLedger, scenarios, resourceAssumptions, evidenceIndex.

각 입력에 provenance와 근거 참조를 붙인다. 단순 문자열 basis만으로 원문을 복제하지 않는다. 근거 ID는 보존하고 원문 확인은 권한이 있는 서버 경로에서만 제공한다. 공개 fixture는 별도 합성 자료로 만든다.

관계는 방향·종류·유효 범위·근거 상태를 보존한다. 과거 한 번의 동승 기록을 모든 상황의 도움 의사로 자동 해석하지 않는다. 기존 대칭 간선 의미를 바꾸는 것은 동작 보존 리팩터링과 분리한다. 실제 자료 변환 시 해석을 임의로 추가하지 않는다.

신규 bundle은 필수 ID·역할 참조·중복·누락을 검증한다. 이장 없는 사례를 허용하되 이장이 필수인 MEDial 운영안을 선택하면 해당 사례에서 사용할 수 없는 이유를 반환한다. 잘못된 role을 임의 주민으로 대체하지 않는다.

### C02 ServiceAdapter

최소 책임: serviceId/version, supportedCases, supportedRules, initialPlan, observation projection에 대한 요구, decision/plan 실행 진입, semantic rule validation과 compile, result interpretation.

코어는 MEDial 이름·P번호·정책 ID 접두어로 분기하지 않는다. 서비스별 이름·지원 기능·상태 설명은 adapter metadata가 제공한다. 실제 외부 시스템 호출, 플러그인 마켓, 범용 DSL, 임의 Python/JavaScript 업로드는 만들지 않는다. 우선 MEDial과 작은 비의료 합성 adapter 두 개로 경계를 검증한다.

기존 Quest/Task는 MEDial adapter의 제한된 의미 단위로 유지한다. 다른 서비스가 모두 의료 Quest 타입을 써야 하는 구조는 피한다. 공통 코어에는 '수정 대상/규칙/실행 기록/평가 근거'만 요구한다.

### C03 하나의 의미 규칙

예시 형태:

```json
{
  "ruleId": "contact-subject.retry",
  "ruleType": "retry_before_help",
  "target": {"questId": "quest:no-response-welfare-check", "taskIds": ["task:contact-subject"]},
  "before": {"count": 0, "intervalMinutes": 20},
  "after": {"count": 1, "intervalMinutes": 20},
  "rationale": "이웃에게 부탁하기 전에 본인에게 다시 확인한다"
}
```

이것은 완성된 기존 API가 아니라 구현 목표 예다. Pydantic discriminated union으로 지원 ruleType별 입력을 정의한다. 동일 구조에서 UI summary, before/after, binding, 실행 semantic hash를 생성한다. 자유 rationale/label은 hash에서 분리한다. 설명만 바꾼 초안을 새 실행 변화로 간주하지 않는다.

검증 순서: baseRevision 일치→고정 입력 불변→근거 참조 유효→지원 ruleType과 사례 적용 가능→값/단위/의존성 일관성→실행 diff 존재→이미 실행한 semantic diff인지→확정. 문자열에 특정 단어가 있는지만으로 의미를 검증하지 않는다.

LLM도 같은 의미 규칙 schema로 제안한다. supportedRules가 없는 변경은 requires_implementation이며 실행하지 않는다. 전후 자연어 문장은 adapter formatter가 만든다. Task 그래프를 실제로 실행할 수 없다면 그래프 편집 가능으로 광고하지 않는다.

### C04 비교와 실행 관측

RunManifest에 CaseBundle hash, 외생 시나리오/seed, 세계·관계·장부·자원·persona/rubric hash, ServiceRevision, 엔진 버전, 역할별 모델/프롬프트/설정, 재생 기록 참조를 둔다. 기존 inputHashes와 ModelPolicy가 이미 제공하는 값을 재사용한다.

고정 입력이 다른 쌍은 통제 비교가 아니라고 표시한다. 서비스 변경에 따른 endogenous 경험 차이는 허용한다. 모델 결과 변이는 별도로 보고한다. 변경 때문에 프롬프트가 달라진 호출은 과거 응답을 억지로 재사용하지 않는다. replay에 없는 호출은 기존 원칙대로 실패로 남긴다.

RuleApplicationRecord: ruleId, eventRefs, conditionStatus, executionStatus, reason. '지원됨', '실제로 적용됨', '결과가 달라짐'을 서로 다른 질문으로 저장한다. 신뢰 점수는 추가하지 않는다.

### C05 근거와 실패 기록

기존 AgentReview/ReviewItem의 6차원, assessment, usageStatus, 경험 사건, evidence refs, unknown, simulated 출처는 보존한다. 무근거 non-unknown과 타인의 사적 사건은 계속 거부한다.

IssueSynthesis의 모든 쟁점/제외 주장은 원본 reviewItemRefs를 가져야 한다. 기술 검사 결과(ref 존재·권한·시점)와 의미 검토 결과(supported/contradicted/insufficient/unreviewed), 라벨 주체(human/AI draft), 검토 이유를 분리한다. 모델이 자기 문장을 검증했다고 사람 검증으로 승격하지 않는다.

BoundaryFinding은 실패 단계(자료/행동/평가/종합/실행/비교), 주장, 적용 manifest, 근거 참조, 판정 주체, 아직 확인할 질문을 가진다. 82문항/20개 seed/종합 라벨 감사는 기존 audit.py 산출물을 재사용하고 적용 조건이 맞는 경우만 보여 준다.

### C06 HumanReview

기존 응답은 보존한다. 새 필드: respondentId, respondentRole, subjectActorId, episodeId, reviewItemRefs, responseStage, disclosureRecordId, answer, correspondence(agreement/correction/disagreement/unknown), correctionTarget, reason, source, consentScope.

기존 partial을 임의로 agreement/disagreement로 변환하지 않는다. 역사 값으로 보존하고 필요하면 사람이 새 정정 레코드를 추가한다. 공개 전 기록에는 correspondence를 요구하지 않는다. 새 schema는 연구자 메모와 주민 직접 응답을 별도 responseKind로 구별한다. 실제 인간 자료가 없는 개발 테스트에는 합성 테스트 레코드임을 명시하고 운영 DB에 넣지 않는다.

### 효율성 작업의 제약

- 서버의 서로 독립적인 detail/generations 읽기는 일관된 revision 확인과 함께 병렬 또는 단일 snapshot API로 정리한다. 단순 병렬화로 서로 다른 시점 데이터를 합치지 않는다.
- 상태 변경 없는 poll에서 큰 review/event 배열을 다시 렌더링하지 않도록 revision/selector를 사용한다. 폴링 도입 자체를 결함으로 취급하지 않는다.
- 에이전트가 경험하지 않은 차원은 기존 계약에 따라 unknown. 그런 경우의 추가 LLM 호출을 줄일 수 있는지 실제 호출 경로부터 확인한다. 성능을 위해 유효 평가를 생략하지 않는다.
- 캐시 키는 입력·모델·프롬프트·관측에 연결한다. 동작이 달라지는 prompt 변경을 성능 리팩터링에 섞지 않는다.

## 8. 단계별 구현 순서와 종료 조건

### Phase 0 현재 기준선과 보존 대상

AGENTS와 최신 문서를 읽고 git status/diff를 확인한다. 기존 사용자 변경을 보존한다. 현재 테스트를 실행해 실제 기준선을 적는다. 합성 데이터의 안부·이동 실행 manifest, 주요 사건/평가/확정 흐름을 fixture로 확보한다. 실제 원자료와 실행 DB는 복사해서 공개 fixture로 쓰지 않는다.

기존 DB schemaVersion, legacy 읽기 전략, migration rollback을 문서화한다. 코드 동작 보존과 연구적 의미 변경을 작업 목록에서 분리한다. 이후 단계가 이 기준선과 다른 이유를 설명할 수 있어야 한다.

### Phase 1 의미 규칙의 단일 경로 P0

C03을 구현하고 기존 지원 규칙을 타입으로 열거한다. 규칙 schema→입력 컨트롤→요약→binding→validator를 한 경로로 연결한다. 직접 작성과 '수정 안 함'을 지원한다. 저장 실패 때 입력 보존. 설명만 바꾸는 경우를 실행 변경으로 받아들이지 않는다. 초안 저장은 실행하지 않고 명시 확정만 자식 실행 하나를 만든다.

인수: 재연락 1→2를 UI에서 변경하면 formatter와 실제 contact 사건이 모두 2회를 나타낸다. afterRule 위조/미지원 rule/고정 입력 변경/중복 확정/기준 revision 충돌을 거부한다. 유효 AI 초안이 0개여도 지원 규칙의 직접 작성은 가능하다.

### Phase 2 주민 평가 중심 UX P1

세 화면 정보 구조를 바꾼다. 평가·근거·쟁점·변경 작성의 직접 연결, 근거 장면 왕복, unknown/미경험 표시, 저장/실행/재생 구분을 구현한다. 기본 반복은 초기안→수정안 한 쌍. 고급 연구 설정과 감사 조회는 접근 가능하되 기본 화면을 점유하지 않는다.

인수: Phase 1의 실제 서버 흐름을 브라우저에서 수행한다. 초안 없음·검증 실패·모델 실패·중간 종료도 빈 화면이 아닌 다음 행동을 제공한다. UI 검증과 실제 디자이너 사용성 검증의 결과를 분리한다.

### Phase 3 자료와 서비스 경계 P1

C01/C02를 구현한다. 은점 특례는 전용 importer/자료로, 합성 자료는 독립 bundle로 분리한다. 신규 누락 장부에 이장 전지 가정을 자동 주입하지 않는다. 기존 MEDial의 사건 순서와 결과를 유지하며 5인/새 ID/이장 없음 fixture를 검증한다. 이후 비의료 합성 adapter 하나로 평가·수정·재실행 계약을 검증한다.

인수: 공통 core의 새 서비스명 분기 없이 비의료 루프가 돈다. 서비스마다 프런트를 복제하지 않는다. 역사적인 MEDial 자료가 신규 사례에 들어가지 않는다. 실제 근거 없는 관계·거절 조건을 새로 만들지 않는다.

### Phase 4 연구의 실패 경계와 현장 기록 P1

C04~C06을 연결한다. 종합에서 제외된 원본 항목을 복원·검토할 수 있고 human/AI draft 라벨이 구분된다. 실제 적용되지 않은 변경과 결과 차이 없음을 구별한다. 공개 전/후 현장 기록을 순서와 참조로 보존한다. 사람 검토가 아직 없으면 0건/미검증으로 표시한다.

인수: 타인 사건·미래 사건·world truth 누출, 존재하지만 의미가 무관한 인용, 종합이 만든 가짜 제외 주장, 공개 전후 혼합을 검사한다. 의미상 지지 여부는 사람이 라벨링해야 할 수 있음을 UI가 명확히 표현한다.

### Phase 5 구조 정리와 문서 완료 P2

엔진과 화면 책임을 분리하고 대체된 타입·API·UI·fixture·테스트를 함께 정리한다. DTO 생성과 migration 검사를 추가한다. 폴링/렌더 성능은 전후 같은 fixture에서 측정한다. 성능 수치를 못 측정하면 구조 개선만 보고한다.

인수: 기본 신규 실행 경로가 하나이며 이전 경로가 우연히 남아 있지 않는다. README→현재 DEVELOPMENT→실행 프롬프트가 같은 상태를 설명한다. 지원되지 않는 기능을 '구현됨'이라고 적지 않는다.

## 9. 테스트와 연구 검증을 구별하기

### 구현에 필요한 회귀 검사

1. 관측 권한: 주민은 자기 경험과 허용 근거만 인용. 세계 전용 사실/타인 비공개/미래 사건 차단.
2. 평가 상태: 미경험은 unknown, 거절/무응답/미해결을 구별. 평가를 총점으로 집계하지 않음.
3. 실행 권한: draft 저장 실행 0회, 이유 없는 확정 거부, 중복 command는 실행 1회, 실패 후 재시도도 중복 실행 없음.
4. 의미 규칙: 타입·단위·범위·사례 지원·현재값 검사, formatter/compiler 일치, 실제 활성 분기를 지나간 기록.
5. 비교: 고정 입력 차이는 별도 실험, replay 누락은 실패, 로그 및 입력 snapshot 불변.
6. 자료 이전: 임의 ID/인원/역할 없음/장부 없음/관계 방향/unknown과 asked_none, 원자료 누출 없음.
7. 현장 검토: 공개 전 응답과 이후 비교 분리, 명시적 disagreement, 응답자와 대상 주민 분리, 정정 append-only.
8. 브라우저: 평가에서 근거 왕복, 저장 실패 입력 유지, 종료/실행/재생의 독립성, 접근성과 작은 화면.

기존 실행 명령을 실제 환경에서 확인해 사용한다: `npm run build`, `npm test`, `python -m pytest server/tests/simulation -q`, `npm run e2e`. e2e는 `playwright.config.ts`의 별도 합성 DB·포트를 사용한다. reset 스크립트가 지우는 경로가 `.run/e2e` 내부인지 먼저 확인한다. 원래 연구 DB를 테스트 DB로 쓰지 않는다. 테스트 숫자는 현재 실행 결과로만 갱신한다.

실제 모델 테스트는 당시 유효한 모델과 설정을 확인하고 제한된 호출 예산에서 수행한다. 기존 기록 replay 검증과 새로운 모델 호출 검증을 구분한다. 실제 모델을 실행하지 못하면 deterministic/fake 통과를 실제 LLM 검증이라고 보고하지 않는다. 원자료 외부 전송이 필요한 경우 기존 동의 범위와 실행 정책을 따른다.

### 논문을 위한 별도 검증

- RQ1: 평가/종합 주장별 근거 지지·모순·부족을 사람이 독립 코딩. 일부 이중 코딩과 이견 해결, 자료 코딩 오류와 모델 오류 구분.
- RQ2: 동일 사건/지표 조건과 평가+근거 추가 조건 비교. 과제·시간·서비스 변경 기능을 맞추고 순서 효과를 통제한다. 발견 수만 세지 말고 관계 부담/소수 의견/변경 이유/현장 질문의 구체성을 본다. 기존 수동 A/B 기능의 유무 비교로 대체하지 않는다.
- RQ3: 실제 주민의 독립 평가 후 agent 평가 공개. 동일 장면/항목에 대한 일치·정정·충돌·모름 기록. 대표성을 검증하지 않은 12인에서 전체 농촌으로 확대하지 않는다.
- RQ4: 자료 공백/거절 비용/관계 전가/미지원 서비스/모델·프롬프트 변경에서 실패 범위를 정리한다. holdout 장면은 prompt를 조정한 장면과 분리한다.

리팩터링 완료는 이 연구가 성공했다는 뜻이 아니다. 연구를 수행하고 반박 가능한 결과를 남길 수 있는 도구가 준비되었다는 뜻이다.

## 10. 구현자가 해서는 안 될 것

- 119·다건 기관 최적화·다일 기억·자유 주민 채팅·완전 자율 일상·3D·범용 정책 언어를 추가하지 않는다. 최신 노트의 향후 항목이 19번의 범위를 자동 해제하지 않는다.
- 주민을 더 협조적으로 만들거나 규칙표와 일치시키도록 프롬프트를 임의 수정하지 않는다. D083과 실패 기록을 보존한다.
- 평가를 좋게 만들려고 세계·관계·persona·평가 rubric을 같은 비교 안에서 수정하지 않는다.
- '코드 전면 리팩터링'을 전체 재작성이나 기존 DB 삭제로 해석하지 않는다. 책임별로 교체하고 작동하던 관측·근거·재현 경계를 지킨다.
- 편집한 자연어와 실행 binding을 또 다른 병렬 상태로 보관하지 않는다.
- 문서와 테스트 수를 맞추려고 기능 검증을 생략하거나 과거 결과를 최신 결과로 바꾸지 않는다.
- 현재 수행하지 못한 브라우저/사람/실제 모델 검증을 완료로 표시하지 않는다.

## 11. 최종 인계 산출물

구현 LLM은 변경 파일, 제거한 옛 경로, schema migration과 rollback, 테스트 결과, 실제 화면 증거, 구현/부분/미구현 표, 남은 연구자 판단을 보고한다. 주요 변경마다 F01~F11 및 RQ1~RQ4 중 무엇을 해결했는지 연결한다. '컴포넌트 분리 완료'만으로 연구·UX 리팩터링 완료를 선언하지 않는다.

# MEDial 다음 제품 방향: 서비스 운영을 함께 설계하는 시뮬레이션 작업대

2026-09-10 · 제안 v0.3. 현재 구현은 DEVELOPMENT.md를 따른다. 이 문서는 다음 설계이며 구현 완료 보고가 아니다.
참고: [추가 문헌과 열람 범위](09_DESIGN_POLICY_REFERENCES.md).

## 1. 제품 정의와 기여 후보

MEDial은 디자이너·보건소 운영자·주민이 의료·돌봄의 서비스 방식, 역할 분담, 정보 공유와 업무 흐름을 만들고, 실제 생활 제약 속에서 실행한 뒤 가정과 설계를 함께 수정하는 도구다.

기대하는 최종 산출물은 다음 네 가지다.
1. 수정 가능한 서비스 운영안: 누가 언제 무엇을 알고 제안/동의/수행/인계하는가.
2. 실행 근거: 조건→결정→실제 사건→개인·기관 결과.
3. 적용 조건: 어느 상황까지 운영안이 성립하며 어디에서 무너지는가.
4. 현장 확인 계획: 어떤 가정을 누구에게 물어보면 다음 설계가 달라지는가.

N01의 경로 기반 설계, N03의 공동 공간, N04의 절차 편집, N05의 현장 왕복, N07의 가정 탐색을 결합하는 것이 제안이다. 각각의 효과가 MEDial에서도 발생한다고 미리 주장하지 않는다.

## 2. 사용자를 구분하되 동일한 기록을 공유한다

| 사용자 | 시작 질문 | 주요 편집 | 가져가는 결과 |
|---|---|---|---|
| 서비스/제품 디자이너 | 주민이 요청하기 어려운 이유는 무엇인가? core item을 어떤 접점으로 구현할까? | 표현 방식, 기기/전화/대면 접점, 요청/동의 순서, 피드백 방식 | 서비스 흐름과 수정 근거, 다음 프로토타입 |
| 보건소 운영자·정책 담당자 | 누가 책임지고 어떤 자원으로 운영 가능한가? | 역할·승인권·업무 분담·인력·허용 부담·인계 조건 | 자원 조건별 운영안, 미해결 사례, 현장 검토용 문서 |
| 주민·이장·실무자 | 이 장면이 우리 상황과 맞나? 누가 부담을 떠안나? | 자신의 행동 가능성/동의/일정에 대한 정정과 이의 제기 | 반영 여부가 보이는 정정 기록 |
| 연구자·모델 관리자 | 어떤 근거와 가정이 결론을 만들었나? | 자료 revision, 모델 기제, 외생 사건, 평가 정의 | 재현 가능한 실행 묶음과 주장 범위 |

별도 앱 네 개를 만들지 않는다. 같은 episode와 설계 revision을 역할별 렌즈로 본다. 외부 정책 담당자용 공개 자료는 별도 익명화 export를 거친다.

## 3. 현재 정책 파라미터 위에 '서비스 기제'를 편집하는 층이 필요하다

현재 연락 간격·상한·우회 허용시간을 바꾸는 것은 중요하지만 core item의 발전 전부는 아니다. 다음 세 설계는 수치가 달라진 하나의 방식이 아니라 서로 다른 서비스 기제다.

예: core item = '주민의 의료 이동을 조율한다'
- A: 필요할 때마다 MEDial이 이웃에게 동승을 부탁한다.
- B: 주민이 사전에 공유한 이동 가능 시간에 요청을 모아 매칭한다.
- C: 보건소가 방문/진료 일정을 묶고 이동 일정을 함께 제안한다.

B의 공유 시간/동의, C의 기관 예약은 추가 기능 가정이다. 현실에 이미 존재한다고 쓰지 않는다. 기관 경유의 가치가 없는 조건도 시험한다.

디자이너는 '장벽 → 서비스 행동 → 기대 기제 → 가까운 결과 → 장기 기대' 카드를 작성한다.
예: 즉석 부탁이 부담스러움 → 가능한 시간을 먼저 자율 등록 → 거절 압박 감소라는 가설 → 연락/거절/중단 횟수 변화 → 지속 이용 기대.
엔진이 직접 계산할 수 있는 것은 중간 사건·시간이다. 압박·지속 이용의 변화는 사람 확인/행동 모델 근거가 없으면 unknown으로 남긴다. CPD의 화살표는 설계 가설이지 실증된 인과관계가 아니다(N01).

첫 버전은 자유로운 노드 편집기 대신 세 가지 템플릿의 단계 순서·담당자·분기 편집을 제공한다. 기술적 구현이 없는 기제는 '아이디어만 작성됨 / 실행 불가'로 남긴다. 자연어가 런타임 코드를 임의 생성/실행하게 하지 않는다.

## 4. 서로 다른 종류의 변경을 명확히 표시한다

| 종류 | 예 | 변경 기록 |
|---|---|---|
| 설계 결정 | 동승 요청 전 동의를 확인, 이장 승인 단계를 생략 | Design/PolicyRevision |
| 운영 자원 | 담당자1명/2명, 근무 구간 | ResourceRevision, 현장값/가정 구분 |
| 불확실한 가정 | 이장이 부재, 연락 가능 시간 해석, 읍내 이동시간 | AssumptionSet |
| 외생 상황 | 두 의료 이동 요청의 중첩, 휴대전화 장애 | ScenarioDeck |
| 행동 모델 | rule/LLM/사람의 개입, 거절 기제의 대안 | ModelRevision |
| 판단 기준 | 기다림과 이장 부담을 어느 수준까지 허용할까 | CriteriaRevision |

유리한 결과를 만들려고 사람 성격이나 평가 기준까지 바꾼 것을 '정책만 바꾼 비교'로 부르지 않는다. 연구 중 판단 기준 자체를 바꾸는 것은 허용하되 이전 기준과 결과도 보존한다.

## 5. 화면 구성: 설계 / 실행 / 비교 / 공동 검토

상단의 네 작업 탭이 동일한 프로젝트·설계·실행을 공유한다.

### 설계
- 상단: core item, 대상 문제, 이번에 확인할 질문.
- 중앙: 주민/이장/MEDial/보건소의 행으로 나눈 서비스 흐름.
- 각 단계: 수행자, 필요한 관측, 권한/동의, 자원, 완료 조건, 실패 후 인계.
- 옆 카드: 기제가 성립하려면 필요한 가정과 현재 근거.
- 실행 버튼 전: 미지원 단계와 누락된 전제만 구체적으로 안내.
- AI 조언은 선택적으로 3개 이내의 대안/반례 초안. 사용자가 채택해야 revision으로 남음.

### 실행
사용자가 원한 좌지도/우상단 MEDial·퀘스트/우하단 대화·이슈 구성을 유지한다.
- 왼쪽: 실제 마을의 2D 지도, 사람·차량·함께 있음.
- 오른쪽 위: 단순 상태 목록을 서비스 행별 실행 흐름과 연결.
- 오른쪽 아래: 현재 중요한 사건과 발화. '이 단계에서 막힘'을 선택하면 필요한 정보·자원·권한을 보여줌.
- 퀘스트를 누르면 해당 이동과 영향을 받은 주민을 함께 강조.
- MEDial 관측/연구자 세계/개인 경험 렌즈를 구분.
- 읽기 전용 질문: '이 판단에 사용된 자료는?'는 근거 조회, 'P3는 왜 이 조건을 거절했나?'는 기록된 이유와 가정. 생성한 설명을 실제 내부 원인으로 둔갑시키지 않음.
- 사람의 역할 대행은 새로운 개입 branch. 사후 면담 답변은 HumanReview이며 과거 실행을 고치지 않음.

### 비교
A/B 긴 표만으로 끝나지 않는다.
- 정책×상황 행렬. 각 칸에서 대표 episode로 이동.
- 행위자별 부담표: 도움받은 사람/도운 사람/기관 각각의 대기·업무·이동·미해결.
- 같은 외생 요청의 최초 분기점→후속 전파를 나란히 표시.
- 평가 기준을 만족하는 조건과 깨지는 조건을 표시. 단일 최고점이나 자동 우승자 없음.
- 모델 내 원인 추적과 현실 인과 추론을 구분. LLM 설명 대신 event causation·변경 입력·예약을 근거로 사용.

### 공동 검토
- 원자료 주장/모델 가정/실행 사건/모의 반응을 구분한 장면 카드.
- 실제 사람은 맞음/다름/판단 어려움, 가능한 대안, 적용 범위를 기록.
- '나는 항상 거절'이 아니라 '이 시간·이 상대·이 요청이면 어렵다'처럼 조건화.
- 주민/이장/기관 간 이견을 하나의 평균으로 합치지 않음.
- 정정은 승인 절차를 거쳐 새 Evidence/ModelRevision으로 반영하고 영향받는 시도를 표시.
- 이전 결과는 그대로 남김. 수정된 모델 재실행 결과를 별도로 비교.

디자인 novelty는 3D 장식보다 지도↔서비스 흐름↔분기 비교↔실제 정정을 연결하는 상호작용에 둔다. 상태를 더 많이 띄우는 것으로 해결하지 않는다.

## 6. 정책 결정자에게 필요한 배치 탐색

초기 예시: 서비스 방식3개×담당자 수3조건×이장 가용성2조건 = 18셀.
모든 숫자/조건은 예시 실험 설계이며 실제 기관 기준이 아니다. 직원0명 조건은 대체 인계/미해결 검사를 위한 stress-test로 표시한다. 운영 부재를 '직원0명인데도 일을 함'으로 흡수하지 않는다.

- 동일한 가정 묶음에서 세 정책은 같은 외생 사건·초기 일과를 사용.
- 과거 보고의 하루1건 외에 두 요청의 시간 중첩 정도를 다음 축으로 추가.
- 알려지지 않은 이동시간은 낮음/중간/높음의 가정 범위로 시험하되 실제 분포라 주장하지 않음.
- rule은 결정적 실행이면 같은 seed 반복이 새 증거를 추가하지 않는다.
- LLM stochastic replicate는 별도 축. policy·world·prompt/model hash를 고정해 모델 변동과 상황 변동을 구분.
- 18셀 중15셀 통과는 '탐색한 조건 중15개'이며 현실 성공 확률83%가 아니다.
- 보건소 운영자가 정한 workload ceiling을 만족하지 않는 장면을 추적. 기준값도 현장 확인 상태를 표시.
- 가정 때문에 선택이 뒤집히면 다음 인터뷰/관찰 대상으로 추천. 정식 value-of-information 계산을 하지 않았다면 해당 용어/점수는 쓰지 않음.

배치가 끝나도 자동 정책 채택은 없다. 최종 출력은 적용 조건과 예외 처리, 반대 의견, 추가로 필요한 근거를 포함한 검토 문서다.

## 7. AI와 MAS의 역할 경계

### 세계 안의 MEDial
당시 받은 관측만 보고 연락/제안/인계/예약을 결정한다. 임상 판단 엔진이 아니다.

### 주민·기관 에이전트
LLM이 필요한 후보: 모호한 부탁 해석, 조건부 수락, 비공개 요청, 대안 시간 제안, 설명을 듣고 질문하기.
규칙/제약 엔진이 맡을 것: 도로·시간·좌석·근무·허용 권한·계약·이벤트 순서.
보건소장은 설정 폼만이 아니라 '새 안부 요청보다 예약된 방문을 우선할지' 등 운영 결정을 하는 역할. 실제 권한과 역할 모델은 직원 검토로 보완.
실무자는 자기 업무 캘린더와 접수된 정보로 처리·추가 정보 요청·연기. 동시에 여러 건을 받아 우선순위와 다른 환자에게 전파되는 지연을 남긴다.

### 세계 밖의 설계 조언 AI
대안 기제, 빠진 이해관계자, 실패 조건, 다음 확인 질문을 제안한다. 주민들에게 미래나 다른 시도의 결과를 흘리지 않는다.
MEDial의 성공을 높이기 위해 주민 페르소나/평가 기준을 몰래 수정할 수 없다.
한 모델을 여러 역할에 쓸 수 있지만 context·memory·저장 권한을 분리한다.
같은 LLM이 제안/주민 반응/성공 평가를 모두 생성한 수치를 검증으로 취급하지 않는다.

N09는 실행과 행동의 분리에 참고하고 N10은 여러 하위 시스템 연결에 참고한다. 특정 프레임워크로 전면 재작성할 이유는 없다. N11의 한계를 고려해 AI가 만들어 낸 자동 합의를 디자인의 정답으로 사용하지 않는다.

## 8. 이슈 생성과 만족도

이슈는 N12에서 영감을 받아 '실패 기제×영향받는 사람×생활 조건' 카드로 생성한다.
예:
- 정보 지연×P9×예약 변경: 병원 시간 변경이 운전자에게 전달되지 않음.
- 요청 집중×P3×기존 근무: 두 요청이 겹쳐 한쪽이 대기.
- 공개 범위×이장×공동체 관계: 필요한 이동 목적보다 상세한 내용이 전달될 우려.
- 기관 과부하×실무자×방문 중: 추가 확인 업무가 기존 방문을 늦춤.
LLM은 actor/event precondition, observation channel, 시간, assumption refs가 있는 초안을 만든다. 엔진이 지원하지 않으면 실행 불가. 발생 빈도는 인간이 지정하거나 근거 자료를 써야 하며 생성 모델이 현실 확률을 정하지 않는다.
'불만족을 생성'하지 말고 시간·선택권·정보 공유 사건을 만들고 그에 대한 반응을 관찰한다.

주민 만족도는 실제 사람 평가와 별도. 모의 반응은 사건+페르소나 근거와 함께 표시한다. 이장 시간 손실/기관 업무/주민 대기는 계산 지표이며 불만의 양으로 환산하지 않는다.
실제 피드백은 actor-reviewer 관계, 시간, 대상 episode, source=human, 동의 범위를 저장한다. 에이전트 발언은 source=simulated로 유지한다.

## 9. 연구 세션 예시: 같은 core item을 세 번 구체화

약60~75분 형성적 워크숍의 제안이며 연구 결과가 아니다.
- 10분: 공동 문제/각자의 우려 작성. 목표는 의료 이동 지원, 우려는 즉석 부탁 부담.
- 10분: A 개별 매칭 설계. 가정·누가 무엇을 아는지 합의하지 못한 부분 표시.
- 10분: P9 이동과 두 번째 요청 장면 실행, P3 충돌 관찰.
- 10분: B 사전 가능 시간 공유로 기제 변경. 주민은 공유 범위에 이의 제기.
- 10분: C 보건소 일정과 함께 조율. 담당자 일정 제약 때문에 다른 부담이 생기는지 탐색.
- 10분: 인력·가용성 가정 변화에서 비교. 서로 다른 우선순위 유지.
- 5~15분: 검토용 운영안과 미확인 질문 작성. 현장 담당자 정정→다음 모델 revision 계획.

성공적인 발견 예: 'B가 만족도 최고'가 아니라 '즉석 매칭을 줄이려면 사전 공유가 필요한데, 주민이 허용하는 정보 범위가 운영 가능성을 좌우한다. 그 범위를 다음 인터뷰에서 확인하자.' 이 문장은 기대 산출물 예시이며 실제 결과가 아니다.

## 10. 다음 구현 우선순위

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| S0 | 귀가 동승 목록 표시 수정, 기존 fork/재생 회귀 유지 | 귀가 사람·차량·좌석·예약 일치. 이는 보고된 남은 문제이며 이번에 재감사하지 않음 |
| S1 | DesignBrief+서비스 흐름 템플릿+가정 카드 | core item 동일 상태에서 서로 다른2가지 서비스 기제를 실행 가능. 문구만 다른 정책은 불충분 |
| S2 | 보건소장/실무자 다건 큐와 결정 기준 | 하나의 요청이 다른 방문의 시간에 영향을 주고 권한·담당자·인계 trace가 있음 |
| S3 | ExperimentMatrix+조건별 비교 | 18셀 rule 실행, 각 결과로부터 episode와 조건 추적, 실패/unknown 보존 |
| S4 | HumanReview+근거 정정 | 실제 사람이 특정 장면에 이견을 남기고 새 모델 revision에 반영, 이전 기록 불변 |
| S5 | 근거 기반 probe와 LLM 제한 적용 | 읽기 전용 질문은 world hash를 바꾸지 않음. 조건부 대안 제안은 허용 행동으로 검증 |
| S6 | 119·다일 기억 | 현재 질문으로 설명 못 하는 필요가 확인되면 확장. 무조건 다음 기능으로 추가하지 않음 |

한 번에 S1~S6 모두 만들지 않는다. S1+S2의 작은 흐름으로 실제 디자이너/기관 담당자에게 보여 주고 S3~S5를 조정한다. 이미 개발된 비교/발견/revision을 재작성하지 말고 확장한다.

# MEDial 화면 재설계 명세
작성: 2026-09-10. 상태: 구현 지시서. 전체 재설계 완료 보고가 아니다.

## 1. 이번 작업의 목표와 적용 순서

사용자는 현재 화면의 디자인과 과도한 버튼 때문에 연구 흐름을 이해하기 어렵다고 평가했다.
목표는 기능 수를 늘리는 것이 아니라, 디자이너가 탐색 질문을 정하고 마을에서 일어난 일을 읽은 뒤 운영안을 비교해 결정할 수 있도록 만드는 것이다.

이 문서는 화면 구조와 상호작용에 관해서 이전 문서의 6~7단계 탭 배치를 대체한다.
12_FINAL_RESEARCH_PLAN.md의 연구 목적, 13_ITERATION_IMPLEMENTATION_SPEC.md의 데이터·실행 계약은 보존한다.
문서끼리 충돌하면 연구 단계는 유지하되 그것을 모두 최상위 메뉴로 만드는 해석을 폐기한다.
기존 사용자 수정, 엔진, 원자료, 로그, 테스트를 초기화하지 않는다.

이번에 직접 한 작은 수정:
- IterationSetup: 가운데 정렬, 760px 최대 폭, 제목·입력 크기·여백 개선.
- 질문과 실행 방식 요약을 먼저 표시하고, 초기안·자원·시나리오·모델·기술 설정을 접힌 실험 설정 안으로 이동.
- SimulationApp: 관찰 화면에서 모든 시도 버튼·비교 추가·수동 실행 도구 묶음을 제거. 수동 비교 화면에서는 유지.
- 관찰 시점 선택은 재생 바의 select로 유지. 지도 해시를 상단에서 제거.
- npm run build 통과. 브라우저 도구 연결 실패로 시각 검증은 아직 하지 못했다.
이 조치만으로 디자인 개선이 완료된 것은 아니다. 다음 명세를 실제로 구현하고 브라우저에서 검증해야 한다.

## 2. 제품이 전달해야 하는 한 문장

“이 마을에 서비스를 이렇게 도입하면 누구에게 어떤 일이 생기고, 무엇을 바꾸면 나아질까?”

주요 사용자는 시스템 디자이너와 정책 결정자다. 주민이 사용하는 의료 앱을 이 화면에 만들지 않는다.
최종 결정은 현장 검토할 운영안의 선택이다. 실제 임상 효과나 실제 주민 만족도를 검증했다는 표현을 쓰지 않는다.
주민 에이전트의 경험 기반 리뷰가 다음 운영안에 연결되는 연구 루프를 화면의 중심으로 삼는다.

## 3. 최상위 화면은 세 개만

상단 내비게이션: [실험 준비] [마을 관찰] [결과 비교].
다음 기능을 별도 최상위 탭으로 두지 않는다: 주민 리뷰, 개선, 세대 선택, 현장 검토, 수동 비교, 발견.
이것들은 삭제하는 기능이 아니라 아래 위치로 통합하는 기능이다.

| 기존 영역 | 새 위치 |
|---|---|
| setup | 실험 준비 |
| cycle | 마을 관찰 |
| reviews | 관찰의 하루 마무리 요약 + 결과 비교의 주민 영향 |
| improve | 결과 비교의 변경 내용 + 결정 필요 시 맥락 안 선택 카드 |
| generations | 결과 비교 본문 |
| field | 비교 화면에서 운영안을 고른 후 열리는 현장 검토 시트 |
| manual | 실험 설정 > 직접 비교 방식, 또는 추가 도구 안 진입점 |
| raw evidence, hashes, JSON paths | 근거 펼치기 / 기술 정보 |
| resident detail, individual conversation | 지도 팝오버의 더 알아보기에서 여는 하나의 상세 패널 |

내비게이션과 상태 표시를 구분한다.
“하루 실행 → 리뷰 생성 → 개선안 생성 → 다음 실행”은 읽기 전용 진행 표시다. 네 개의 액션 버튼으로 만들지 않는다.
버전 선택은 하나의 select다. 버전마다 버튼을 만들지 않는다.
현재 처리 버전과 현재 관찰 버전이 다를 때 둘을 짧게 구분한다. 과거를 읽어도 실행 중인 루프는 바뀌지 않는다.

## 4. 화면 A: 실험 준비

최초 빈 상태에서 보이는 내용:
1. 제목 “어떤 서비스를 탐색할까요?”
2. 설명 한 문장.
3. 탐색할 질문 입력. 이것을 자유 텍스트 실행 명령으로 해석하지 않는다.
4. 초기 운영안 select. 기존 계약으로 실행 가능한 정책만 표시.
5. 접힌 “실험 설정”. 요약은 “최대 3개 버전 · 시나리오 N개 · 규칙 기반 리뷰”처럼 실제 상태에서 생성.
6. 주 버튼 “실험 시작”.

실험 이름은 질문에서 초기값을 만들고 이름 변경은 부차적으로 제공한다.
초기 운영안의 설명은 “누구에게 먼저 연락하고, 언제 다음 단계로 넘기는가”처럼 자연어 2~3줄로 보여준다.
core item만 바꾸면 실행 정책까지 자동으로 바뀌었다고 오해하지 않도록 질문과 실행 규칙을 분리한다.
정책 생성 기능이 없으면 자유 질문을 정책으로 변환한 것처럼 표시하지 않는다.

접힌 설정 안에 자원, 시나리오 선택, 반복 상한, 후보 상한, 리뷰/개선 생성 방식, 비용 제한, 자동 변경 범위, 실행 한계를 배치한다.
자동 변경 허용 범위는 사람 말로 요약하고 실제 필드 경로는 그 아래 근거로 펼친다.
미구현 목록, API 제공자, 데이터 해시, 긴 연구 설명은 기본 화면을 차지하지 않는다.
규칙 기반/LLM/혼합 및 실제 평가가 아니라는 구분은 짧은 요약으로 항상 확인 가능해야 한다.
실행을 막는 오류·입력 누락·비용 상한은 접힌 설정 안에 숨기지 않는다.
현재 callBudget=0이 무제한을 뜻한다면 그 계약을 몰래 바꾸지 않는다. LLM을 켤 때 무제한 여부와 상한을 명확히 표시하고, 연구용 기본값은 명시적인 유한 예산을 검토한다. 임의 예산을 사용자가 정한 값처럼 기록하지 않는다.

단일 시작 버튼 구현:
createSession 완료 후 반환된 sessionId에 start 명령을 정확히 한 번 전송한다.
기존 store의 createSession은 오류를 내부 처리할 수 있으므로 단순 await 뒤 start를 호출하지 않는다.
새 action이 성공 여부/ID를 명시적으로 반환하게 하거나 원자적인 UI 명령 흐름을 작성한다.
중복 클릭 잠금, create 실패, start 실패, 이미 실행 중인 응답을 각각 처리한다.
start만 실패했다면 새 세션을 또 만들지 않고 해당 세션의 시작을 재시도한다.
새로고침 시 자동 start를 반복하지 않는다.
설정과 기존 자료를 불러오기만 했는데 새 A/B 실험이 자동 생성되는 bootstrap 동작은 제거한다.
최초 상태는 조작 가능한 준비 화면이고, 예제는 사용자가 선택했을 때만 연다.
빈 상태의 지도 렌더링이 loaded attempt에 묶여 있는 현재 조건도 함께 분리한다.

## 5. 화면 B: 마을 관찰

1440×900 기준 구조:

MEDial             실험 준비  마을 관찰  결과 비교            실험 이름
버전 v1 관찰 중     하루 실행 → 주민 리뷰 → 개선안 → 다음 실행   실행 상태
┌──────────────────────────┬──────────────────────┐
│ 은점마을                  │ MEDial / 현재 처리   │
│                          │ 선택한 요청의 흐름   │
│ 실제 지도 + 주민 + 차량   ├──────────────────────┤
│                          │ 지금 일어난 일       │
│                          │ 사건/대화/하루 리뷰  │
├──────────────────────────┤                      │
│ 마을 밖  P2 · 남해읍      │                      │
│ 09:30  재생  ━━━━━━━      │                      │
└──────────────────────────┴──────────────────────┘

치수:
- 앱 헤더 56px, 진행 표시 44px. 두 줄보다 많은 상시 도구 바 금지.
- 본문 가용 폭에서 우측 400px(최소360, 최대440), 좌측 나머지. 패널 간격16px, 외곽20px.
- 지도는 본문 높이를 우선 사용. 하단 재생 바는 지도 내부 레이아웃의 별도 행, 지도 위 overlay가 아니다.
- 우측 상단은 약 1/3, 하단은 나머지. 긴 로그 때문에 지도가 줄어들지 않는다.
- 1100px 미만에서는 우측을 340px로, 900px 미만에서는 지도 위·요약 아래 단일열. 가로 스크롤로 숨기지 않는다.
- 1366×768과1440×900에서 기본 화면 전체에 가로 넘침이 없어야 한다.
- 장식용 카드, 거대한 KPI, 항목마다 컬러 테두리를 추가하지 않는다.

지도에 대한 구체 지시:
- 실제 원자료 지도, 북쪽 위, 평면 2D 유지. 기울임, 원근, 가짜 3D 건물, 농장/집 창작 금지.
- 남북으로 긴 실제 지형의 비율을 보존한다. 빈 여백을 없애려고 가로로 늘리거나 지점을 이동시키지 않는다.
- 지도 이미지·도로·장소·주민·차량을 동일한 투영으로 배치한다. CSS 회전과 SVG 좌표 회전을 섞지 않는다.
- 최초 fit은 마을 본체와 필요한 해역을 대상으로 한다. 마을 밖 읍내 좌표 때문에 전체 지도를 축소하지 않는다.
- 지도 배경은 낮은 채도, 중요한 사건만 강조. 바탕 지도 위에 또 다른 도로/지명 전체를 중복해서 그리지 않는다.
- 원자료 raster라면 일부 지명을 CSS로 지울 수 있다고 가정하지 않는다. 새 타일 서버나 재제작 지형으로 대체하기 전에 현재 raster+overlay 중복부터 해결한다.
- 항구·회관·보건소 등 필요한 지명만 해당 줌 레벨에 표시. 실명 주택 라벨은 노출하지 않는다.
- 주민 얼굴 표시 지름22px, P번호13px. 상호작용 hit area는 별도 최소32px. 활동 아이콘은8~10px 한 개.
- 이장은 “이장”, 나머지는 P1~P12. 보건소/119는 별도 기관 또는 역할 표시. 자료에 없는 사람을 실제 주민처럼 추가하지 않는다.
- 차량은 최소28×16px 실루엣과 색 대비로 구분한다. 동승자는 지도에 중복 보행자로 그리지 않는다.
- 운행 구간의 탑승 현황은 예약/사건에서 계산한다. 귀가 구간이 빈 차로 보이는 문제는 데이터와 렌더 경계를 확인해서 수정한다.
- 같은 장소의 사람은 하나의 group anchor에 최대3개 얼굴+인원수. 장소 동일성과 실제 동승/동행을 기준으로 묶는다.
- 화면상 가까울 뿐인 사람을 같이 대화하는 것으로 만들지 않는다. 픽셀 충돌 회피와 사회적 집단을 분리한다.
- 충돌 때문에 마커를 옮길 때 작은 leader line으로 실제 anchor에 연결한다. 줌 변경 중 집단 구성이 임의로 바뀌지 않는다.
- 선택한 사건의 관련자/경로만 강조하고 나머지는 약하게 유지. 전체 도로망·모든 이동선은 기본 숨김.
- 마을 밖 주민은 지도 아래 단일 접힘 목록, 이름·장소·현재 일. 지도 여백이나 임의 바깥 좌표에 놓지 않는다.
- 도구는 확대/축소/전체보기, 작게 묶어 한 곳에 둔다. “이름/얼굴/상태/경로” 토글을 상시 나열하지 않는다.
- OSM 저작자 표시와 필수 출처 표시는 남긴다.

그룹 팝오버:
- hover 또는 클릭/키보드 focus로 같은 팝오버를 연다. 동시에 하나만 열린다.
- 폭240~280px. 상단 장소명, 사람 선택 가로 목록, 선택한 사람의 현재 일 한두 줄, 작은 “더 알아보기”.
- 사람이 많으면 가로 스크롤이나 두 줄까지 허용. 모든 주민의 긴 프로필을 동시에 표시하지 않는다.
- 현재 사건에 연결된 대화가 있으면 한 줄 발췌. 없으면 현재 일만 보여준다. 대화 창작 금지.
- 팝오버로 포인터를 옮기는 동안 닫히지 않아야 한다. Escape/바깥 클릭으로 닫고 원래 마커에 focus 복귀.
- 화면 상하좌우 clamp/flip. 팝오버가 자기 anchor를 가리지 않도록 여유16px.
- 더 알아보기는 우측 상세 drawer 하나를 연다. 중첩 모달 금지.
- 상세에는 오늘의 일과/시스템 이용 경험/리뷰/개별 대화 접근을 모은다.
- 읽기용 질문과 세계를 바꾸는 개입은 명시적으로 분리하며 기존 probe/fork 계약을 유지한다.

우측 상단 MEDial:
- 현재 상태 한 문장. 예: “P1의 응답을 기다리고 있습니다.” 문장은 실제 사건으로부터 결정한다.
- 해당 요청에 대한 관측→판단→조율→결과의 간결한 세로 흐름.
- 여러 요청을 모두 섞어 완료 상태로 칠하지 않는다. task/request correlation ID 기준 selector를 작성한다.
- 해당 ID가 데이터에 없다면 화면에서 상상해 묶지 말고 필요한 최소 계약 보완을 보고한다.
- “MEDial이 알고 있는 것”을 근거로 판단 이유 한 줄, 상세 근거는 펼치기.
- 보건소와119가 현재 사건에 참여할 때 흐름에 등장. 미구현 출동을 장식 애니메이션으로 완료 처리하지 않는다.
- 운영 조건 편집 버튼은 여기에서 제거하고 비교/준비의 수정 흐름으로 통합한다.

우측 하단:
- 제목 “지금 일어난 일”. 기본은 현재 커서까지의 의미 있는 사건, 최신 관련 항목이 보인다.
- 연락 시도/수락/이동/만남/문제 종료를 인간이 읽을 수 있는 짧은 문장으로 보여준다.
- raw event 명칭, 동일한 시간의 기술 사건 여러 개, payload를 기본 목록에서 숨긴다.
- 여러 사건을 요약해도 원 사건 ID와 순서로 돌아갈 수 있어야 한다.
- 목록 클릭은 해당 장면의 읽기만 한다. 새로운 LLM 호출이나 개입을 만들지 않는다.
- 하루가 끝나면 같은 영역에 “하루를 마친 주민들의 리뷰”를 표시한다. 별도 화면 찾아가기를 요구하지 않는다.
- 대표 요약을 보여주되 반대 의견/부담이 늘어난 주민을 지우지 않는다. 전체12명은 펼쳐볼 수 있다.
- 자동 루프가 빨리 끝나도 각 버전의 하루/리뷰/개선 근거를 다시 볼 수 있다. 로딩 애니메이션으로 계산을 연출하지 않는다.

재생:
- 기본 컨트롤은 재생/정지, 시각, 타임라인. 사건 단위 앞뒤/처음으로는 추가 컨트롤에 둔다.
- “기록 재생”과 “연구 실행 중/중지”는 다른 상태와 제어다. 재생 정지가 서버 루프 정지처럼 보이면 안 된다.
- 서버가 계산 완료했어도 기록 재생이 계속 가능하다. 재생 위치로 미래 리뷰 내용을 과거 인식처럼 섞지 않는다.
- 실행 일시정지/재개/종료는 진행 표시의 상태별 제어 한 곳에만 제공한다.

## 6. 화면 C: 결과 비교

제목 “무엇이 달라졌나요?”
기본 비교는 초기안과 선택한 개선안. 버전 선택은 각 열 상단 select 두 개.
초기에는 가장 최근 완료된 개선안을 보여줄 수 있으나 “최고안”으로 표시하지 않는다.
모든 버전 표는 아래 “전체 시도 보기”로 접근한다.

기본 비교표 행:
- 바꾼 운영 조건: 이전 → 이후, 바꾼 이유와 연결된 주민 리뷰.
- 요청 해결/미해결 및 소요 시간: 단위, 분모, 집계 범위.
- 주민/이장/보건소 담당자의 부담: 총량과 가장 부담이 큰 사람.
- 서비스 이용 횟수: 시뮬레이션 기간 내 횟수. 미사용/이용 기회 없음 구분.
- 주민 에이전트 리뷰: 긍정/부정/혼합/판단 불가 + 근거 있는 인용.
- 새로 발생한 문제와 악화된 점.
전체 항목을 합친 임의 만족도 점수, fake percent, 승자 트로피, 자동 채택 금지.
현재 데이터에 없는 지표는 “미수집”으로 표기하거나 해당 행을 생략한다. 숫자를 채우지 않는다.
정책 외에 시나리오/seed/자원/페르소나가 바뀌었다면 비교 가능성 차이를 표의 조건 요약에 드러낸다.

표 아래 “다음 시도에서 바꾼 이유”:
주민 경험 → 리뷰 → 개선 제안 → 실제 변경 → 결과 차이의 연결을 한 단위로 읽게 한다.
기술 JSON diff는 펼친다. 소수 의견과 해결 못한 점을 함께 둔다.
needs_decision이면 대안의 이익/비용/근거를 나란히 제시하고 사용자가 하나를 선택해 계속한다.
이 상황에서만 “이 방향으로 계속”을 주 버튼으로 한다. 매 세대마다 불필요한 승인 화면을 넣지 않는다.

루프 종료 후 주 버튼은 “현장에서 검토할 안 선택”.
선택하면 측면 시트에서 이유, 감수할 부담, 미해결 질문, 현장 인터뷰 질문을 작성·확인한다.
유지/보류/기각도 선택 가능해야 한다. 버튼 누름을 실제 서비스 도입 승인으로 해석하지 않는다.
실제 인터뷰 응답 입력은 현장 검토 문서 안 별도 영역에 둔다.
synthetic review와 human review는 다른 데이터·라벨·시점으로 보존한다.
운영안을 더 바꾸고 싶으면 선택한 버전을 기반으로 새 실험 준비로 돌아간다. 기존 결과 덮어쓰기 금지.

## 7. 시각 디자인 규칙

목표: 조용하고 정밀한 연구용 워크스페이스. 생동감은 지도 위 사람·차량·장면 연결에서 나온다.
Simile 참조의 핵심은 하나의 마을에서 여러 사람이 살아가는 가독성이다. 게임 스프라이트·도시 건물의 복제가 아니다.

토큰:
- app background #F7F8FA, surface #FFFFFF, text #1D2935, secondary #596775, border #DDE3E8.
- primary #25665B, selected background #EAF3F0. 경고 #9A651D, 오류 #B23A35.
- 상태는 색과 텍스트 함께. 장식 색상 남발 금지. unknown은 중립색.
- 본문14px/line-height1.55, 보조12px, 섹션18px, 페이지24px, 브랜드18px.
- 지도 작은 지명/필수 출처 외9~11px 텍스트를 화면 주 정보로 사용하지 않는다.
- 4/8/12/16/24/32 간격, 패널 radius10px, 작은 컨트롤6px.
- 버튼 높이36~40px. primary 한 개/작업 영역, 나머지는 secondary 또는 의미 있는 텍스트 링크.
- 그림자는 팝오버/drawer에만 약하게. 배경 그라디언트, 유리 효과, 떠 있는 KPI 카드 금지.
- 일반 행은 카드로 감싸지 않는다. 구분선과 여백으로 구획한다.
- hover 가능한 것과 단순 상태 텍스트를 구분한다. 행 전체를 이유 없이 button으로 만들지 않는다.
- 키보드 focus outline을 없애지 않는다. 최소 대비4.5:1을 확인한다.
- 움직임은 위치 변화에만 사용. prefers-reduced-motion 대응. 화면 전환 과장 금지.
- 새 UI 프레임워크나 지도 라이브러리를 이 작업 때문에 추가하지 않는다. 현재 React/styled-components/SVG를 활용한다.

## 9. 수용 기준: 코드 통과만으로 완료 보고 금지

실제 브라우저에서1366×768,1440×900 확인. 완료 보고에 최소 다음 화면의 스크린샷 경로를 남긴다.
A. 새 실험 준비: 질문/초기안/설정요약/시작만 명확하게 보임.
B. 관찰: 그룹 팝오버가 열린 지도, 우측 한 요청의 흐름, 마을 밖 목록.
C. 결과 비교: 바뀐 조건, 주민 리뷰, 악화된 점, 현장 검토 선택.
D. needs_decision 또는 오류 상태: 다음 행동이 한 곳에 분명히 보임.

검증 시나리오:
- 새 브라우저 상태 진입만으로 새로운 A/B 시도가 생성되지 않는다.
- 질문/초기안 지정 후 시작 한 번으로 생성→실행→관찰. 더블클릭해도 중복 세션 없음.
- create 실패/start 실패 구분, start 재시도가 새 세션을 만들지 않음.
- 그룹 얼굴 선택/hover 이동/Escape/더 알아보기, 지도 네 모서리에서 팝오버 잘림 없음.
- 마커와 지명 충돌,12명 회관 집합,차량 동승/귀가,마을 밖 인물 확인.
- 작업별 MEDial 흐름이 다른 요청의 사건을 섞지 않음.
- 기록 재생 정지와 루프 중지가 독립. 과거 버전 열기가 실행 상태를 변경하지 않음.
- 주민 리뷰 근거 클릭이 정확한 버전/시점으로 이동하며 새 모델 호출을 만들지 않음.
- 루프완료→비교→안 선택/보류→현장 질문 확인까지 경로가 끊기지 않음.
- 새로고침/서버 재시작 후 session/버전/cursor 복원.
- 오류·판단 불가·미수집·합성/실제 구분 보존.
- npm run build 및 기존 회귀 검사. 상태변경/복원/중복시작/요청그룹 selector만 의미 있는 추가 검사 작성.
- 정적인 CSS값을 복제하는 테스트는 만들지 않는다.

간단한 사용자 과제:
연구자가 설명 없이 “첫 실험 시작”, “P1에게 생긴 일 보기”, “v0와v1의 차이 찾기”, “현장에서 확인할 질문 정하기”를 수행할 수 있는지 관찰한다.
개발자 내부 확인과 실제 사용자 사용성 평가는 구분해서 보고한다. 사용자를 테스트하지 않았다면 사용자 검증 완료라고 쓰지 않는다.

## 10. 완료 보고 형식

- 실제 바뀐 기본 작업 흐름을 세 문장으로 설명.
- 수정 파일과 실행한 검사, 위A~D 스크린샷.
- 그대로 보존된 계약 중 중요한 것: 관측 경계, 불변 로그, 원자료 좌표, 실제/합성 구분.
- 구현하지 못한 항목과 이유. 브라우저에서 못 봤으면 그 사실 명시.
- 작은 CSS 수정만 하고 전체 UX 리디자인 완료라고 쓰지 않는다.

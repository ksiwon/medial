# MEDial 최종 연구·제품 기획 v1

상태: 2026-09-10 사용자 연구 구상에 따른 구현 목표. 구현 완료 문서가 아니다.
이번 사용자 요청을 우선하며 이전 09~11의 서비스 설계 기능은 아래 리뷰 기반 반복 구조를 지원하는 기능으로 통합한다. 현재 구현 사실은 DEVELOPMENT.md를 따른다.

## 1. 연구 제목과 목적
가제: MEDial — 인터뷰 기반 마을 에이전트의 경험 리뷰를 활용한 의료·돌봄 시스템 반복 설계 도구.

초기 현장 인터뷰로 주민과 생활 환경을 모델링하고, 설계한 의료·돌봄 AI Orchestrator를 가상 마을에 도입한다. 각 에이전트가 경험한 서비스를 리뷰하면 이를 바탕으로 MEDial의 운영안을 수정하고 다시 실행한다. 디자이너는 여러 세대의 변화·부작용·미확인 조건을 비교해 현장에서 검토할 운영안을 선택한다. 이후 재방문 인터뷰에서 모의 반응과 운영안의 타당성을 확인한다.

연구 동기: 농촌 고령자와 장기간/반복적으로 인터뷰하며 AI 서비스를 개선하는 과정은 참여·설명·방문 부담이 클 수 있다. 이것은 본 연구에서 현장 자료로 구체화할 문제 진술이다. 모든 고령자가 인터뷰하기 어렵다는 일반화는 하지 않는다.
시뮬레이션은 현장 반복 중 사전 설계 탐색 일부를 대신한다. 실제 만족도, 장기 이용, 의료 효과와 안전을 확정하는 대체 실험으로 주장하지 않는다.
현장 재방문은 부록 검증이 아니라 연구 루프의 필수 마지막 단계다.

## 2. 연구 질문
RQ1. 인터뷰 기반 주민 에이전트의 경험 리뷰가 어떤 문제·개선 기회를 드러내며 실제 주민의 정정과 어디서 일치/충돌하는가?
RQ2. 리뷰→개선→재실행 과정이 디자이너의 운영안 구체화·대안 탐색·의사결정 근거 형성에 어떻게 기여하는가?
RQ3. 개선으로 누구의 이익/부담이 바뀌며 어떤 가정·서비스 조건에서 개선이 유지되거나 무너지는가?
RQ4. 이 도구로 사전 탐색할 수 있는 영역과 실제 현장 참여가 반드시 필요한 영역은 무엇인가?

기여 후보: 인터뷰 근거→경험 사건→행위자별 리뷰→운영 정책 patch→다음 세대의 결과→실제 정정까지 연결하는 상호작용과 데이터 구조; 농촌 의료·돌봄의 관계·이동·기관 부담에 대한 사례; 그 효용과 한계를 보여주는 디자이너/현장 연구.
'처음으로 에이전트가 리뷰한다' 혹은 '현장 인터뷰를 대체한다'는 최초성/유효성 주장을 하지 않는다. 기존 문헌과 차이를 최종 논문에서 좁혀 검증한다.

## 3. 사용자가 제시한 11단계의 실행 명세

| 단계 | 수행 | 산출물 |
|---|---|---|
| 1 현재 상황 인터뷰 | 주민의 일과·관계·의료 접근·도움 요청·디지털/AI 경험 조사 | SourceRecord, 근거와 동의 범위 |
| 2 개인 에이전트 제작 | 인터뷰 주장/해석/가정/unknown을 분리하고 개인별 관측·기억·행동 경계 설정 | PersonaRevision, EvidenceCard |
| 3 마을 MAS 구축 | 공간·도로·시간·일과·관계·기관·차량을 연결 | WorldRevision, ResourceRevision |
| 4 AI Orchestrator 도입 | core item과 초기 서비스 절차/정책을 고정 | DesignBrief, PolicyRevision v0 |
| 5 1 Cycle | 일정 기간의 일상과 필요 발생, 서비스 사용·거절·실패를 실행 | Attempt, 사건 로그, 실제 수행 이력 |
| 6 에이전트 리뷰 | 경험한 장면과 페르소나 근거로 개인 리뷰 작성 | AgentReview, 객관 지표 별도 |
| 7 MEDial 개선 | 리뷰의 공통점·충돌·불확실성 분석, 수정안 제안·검증·선택 | ReviewSynthesis, ChangeProposal, v1 |
| 8 개선안 재실행 | 고정된 비교 조건으로 v1 실행 | 새 Attempt, 전후 비교 |
| 9 반복 | 같은 구조로 여러 세대 실행하고 개선 정체/회귀 확인 | IterationSession, 계보 |
| 10 디자이너 결정 | 운영안 선택/보류, 선택 이유와 반대 의견·적용 조건 기록 | DecisionRecord, 현장 검토 패키지 |
| 11 재방문 인터뷰 | 짧은 장면을 보여주며 반응·가정·운영안 정정 | HumanReview, EvidenceRevision, 다음 연구 질문 |

현재 자료는 P1~P12의 참여자 모델이다. '전 주민 모델링'은 목표 범위이지 확보된 사실이 아니다. 미포함 주민/가족/기관 종사자는 unknown 또는 별도 합성 역할로 표시한다. 이장은 P6와 같은 한 사람이다.

## 4. Cycle, 세대, 반복 실행, 다일 실행을 구분

Cycle: 한 정책 버전으로 정해진 기간을 실행하고 개인 리뷰를 수집하는 단위.
Generation: 해당 Cycle 리뷰를 근거로 운영안을 바꾼 설계 세대. v0→v1→v2.
Attempt: 특정 입력/seed/adapter로 실행한 개별 로그.
Replicate: 같은 입력의 모델 변동을 보기 위한 재실행.
Longitudinal run: 다음 날로 기억·미해결 요청을 이어가는 시간 경과.

기본 연구 모드:
- 한 Cycle은 하루. 첫 프로토타입은 가정된 개발 상황에서 v0 포함 최대3세대를 자동 진행.
- 세대 비교 때 시작 일과/자원/주민 기억/외생 사건을 같은 snapshot으로 되돌린다. 정책만 변경한다.
- 주민이 v1에 v0의 불만을 기억하는 것은 기본 모드에서 금지. 그렇지 않으면 정책과 학습/친숙함 효과가 섞인다.
- 다일 모드는 추후 별도 지원. 같은 정책으로3~7일 진행하고 날 사이 기억을 이어간다. 정책 변경 후 적응 연구는 별도 longitudinal 조건으로 기록.
- 하나의 성공 상황을 반복 재생하며 개선됐다고 주장하지 않는다. 개발 deck과 개선 모델에 미공개인 검토 deck을 분리한다.

3세대, 하루, 검토 주기 등은 제품 기본값 제안이며 통계적/임상적 기준이 아니다. UI에서 설정 가능하다.

## 5. 네 역할의 권한 분리

1) 세계 엔진: 시간·위치·자원·사건을 확정한다.
2) 세계 안의 MEDial: 관측으로 요청 해석/연락/배정/동의/인계를 수행한다.
3) 주민·기관 에이전트: 자기 정보로 행동하며 Cycle 종료 시 자신의 서비스 경험을 리뷰한다.
4) 세계 밖의 개선 에이전트: 리뷰·근거·집계 지표로 MEDial 변경안을 제안한다.

세계 밖의 개선 에이전트가 세계 진실을 참고한 발견은 designer-only로 표시한다. MEDial의 실행 정책에 비관측 위치 등 미래/숨은 사실을 주입하지 않는다.
디자이너는 목적·허용 변경·평가 기준·예산·최종 선택을 소유한다.
같은 LLM을 각 역할에 사용할 수 있지만 메시지/기억/권한은 분리한다. 다수 모델 투표를 실제 주민 합의로 해석하지 않는다.

## 6. 개인 리뷰가 핵심 기능이다

리뷰는 모든 개인에 대해 호출할 수 있지만 미사용/미경험이면 평가 없음 또는 unknown을 반환한다. 미사용은 관찰 결과이며 무조건 실패/불만족이 아니다.
기본 질문:
- 이번 Cycle에서 어떤 일을 요청하거나 제안받았는가?
- 실제로 무엇이 도움이 됐고 무엇이 불편했는가?
- 시간·이동·선택권·정보 공유 측면에서 어떤 일이 있었는가?
- 다음에 이용한다면 어떤 조건이 달라져야 하는가?
- 답할 근거가 없는 부분은 무엇인가?

AgentReview 최소:
actorId, attemptId, policyRevision, source=simulated, adapter=rule|llm,
experiencedEventIds, evidenceRefs, usageStatus,
items[dimension, assessment=positive|mixed|negative|unknown, reason, eventRefs, requestedChange],
overallNarrative, unknowns, model/promptVersion.

평가 차원: 도움/해결, 시간·노동, 선택·거절, 공개 범위, 이해 가능성, 재이용 조건.
실제 감정/만족 확률을 수치로 날조하지 않는다. 설계자가 원하면 순서형 척도를 추가하되 simulated이며 사람 척도와 분리한다. 초기 기본은 서술+차원별 평가다.
기관 실무자/소장의 리뷰도 별도로 받는다. 주민 만족이 올라가면서 실무자 과부하가 생기는 충돌을 남긴다.
리뷰 근거 이벤트는 그 actor가 경험한 것만 허용한다. 집계 지표로 리뷰를 만들어 넣지 않는다.
리뷰 reason은 모델이 제시한 근거 기반 설명이며 LLM 내부 인과의 증거가 아니다.

## 7. 리뷰를 어떻게 개선으로 바꾸는가

ReviewSynthesis:
문제별 리뷰 묶음, affectedActors, dissentingActors, eventRefs,
underlyingAssumptions, objectiveMetrics, alternativeExplanations, unknowns.

최다수 의견만 채택하지 않는다. 소수지만 큰 불편, 보건 인력의 추가 노동, 사용하지 못한 사람을 별도로 보인다.
개선 에이전트는 한 세대에서 최대2개 수정 후보를 제안한다. 후보마다:
- 해결하려는 리뷰 항목과 관련 사건
- 기대하는 작동 기제
- 변경 전/후의 정확한 값 또는 절차
- 영향을 받을 다른 사람
- 예상 부작용과 필요한 가정
- 다음 Cycle에서 확인할 지표/장면

허용 범위:
연락 시간/횟수/채널, 도움 요청 순서, 우회 허용시간, 정보 최소화, 인계 시점,
지원되는 서비스 단계 순서·담당자·동의 절차.
금지 자동 변경:
페르소나/인터뷰 근거/초기 기억/외생 사건의 난도/평가 rubric/세계 사실,
인력·차량을 예산과 무관하게 추가, 임상 기준 생성, runtime 임의 코드 수정.
자원 증원은 별도 운영안/ResourceRevision이며 policy-only 비교에서 분리한다.
지원되지 않는 서비스 기능은 '새 구현 필요' 제안으로 남기고 자동 실행하지 않는다.

## 8. 자동 반복과 디자이너 통제

기본: 제한된 자동 반복. 사용자가 시작 전에 세대 수·모델 호출 예산·허용 필드·검토 기준을 확인하고 '반복 시작'하면 매번 승인 없이 진행한다.
현재 generation을 리뷰→분석→후보 검증→후보 실행→비교한다.
지배되는 후보(모든 지정 지표가 같거나 나쁘고 하나 이상 나쁨)는 진전 후보에서 제외할 수 있다. unknown이 있으면 우열을 단정하지 않는다.
하나의 후보가 명확히 우세하고 필수 제약을 통과하면 다음 세대로 이어간다. 여러 후보가 trade-off이면 분기 후보로 보존하고 기본은 needs_decision으로 멈춘다. 사용자가 사전 지정한 선택 기준이 있으면 그 기준으로 선택하고 기록한다.
'리뷰가 긍정적'만으로 채택하지 않는다. 이웃·기관 burden과 미해결, 동의·관측 위반을 같이 본다.
정체, 반복 patch, 모든 후보 무효, 예산 종료, API 장애, trade-off로 결정 필요는 각각 별도 stopReason. 모두 성공 완료로 표시하지 않는다.
최종 채택은 항상 디자이너가 한다. 가장 마지막 세대가 자동 우승자가 되지 않는다.
별도 수동 모드는 세대마다 후보를 고를 수 있다.

## 9. 예시: 실제 결과가 아닌 목표 데모

v0: P9 이동 필요→P3 동승, 두 번째 요청 충돌.
P3 모의 리뷰: '도움은 줄 수 있지만 바로 이어지는 부탁은 어렵다.' 근거는 해당 예약·요청.
개선 후보 v1: 이미 약속한 운전자의 추가 우회 제한 또는 다른 가능 시간 제안.
재실행: 충돌은 줄지만 P9 대기 증가 가능. 개선 결과가 mixed면 그대로 표시.
기관 리뷰/객관 결과: 대체 인계가 늘어 실무자 업무가 증가할 수 있음.
v2 후보: 지원되는 사전 가능 시간 확인 절차로 변경. 미구현이면 자동 적용 금지.
최종 디자이너: v1 선택/보류, 이유와 조건을 기록. 이웃 부담 vs 주민 대기 trade-off를 현장 인터뷰 질문으로 보냄.
어떤 리뷰/성공 결과도 미리 시나리오에 고정해 점차 좋아지는 연출로 만들지 않는다.

## 10. 화면

상단: 연구 질문/core item · Iteration session · v0/v1/v2 · 현재 단계 · 실행/정지.
탭: 설계 / Cycle 실행 / 에이전트 리뷰 / 세대 비교 / 현장 검토.
Cycle 화면: 기존 북쪽 위2D 실제 지도, 작은 얼굴·별도 차량·그룹 팝오버·밖 주민 유지.
우상단: MEDial 실제 결정과 퀘스트 상태. 우하단: 현재 사건/발화.
리뷰 화면: P1~P12·이장·기관별 카드. 사용/미사용, 장면 링크, 개인 요청, unknown 표시. 리뷰에서 근거 장면으로 seek.
개선 화면: 공통 문제·이견·patch·영향·허용 범위. 개선 AI와 MEDial 상태를 혼동하지 않게 라벨.
세대 비교: 변경 diff, 유지 입력, 사람별 득실, 전체 지표, 분기 계보. 원자료 해석 변화와 정책 변화 구분.
현장 검토: 선택 운영안, 대표 장면3~5개, 반대 의견, 질문, 실제 답변 입력.
세대 재생과 현재 run 실행을 혼합하지 않는다. 자동 진행 중에도 이전 세대 기록을 읽을 수 있다.

## 11. 평가와 재방문

소프트웨어 검증: 재현·관측·자원·분기·불변 저장·리뷰 근거·patch 경계.
주민 에이전트 적합성: 초기 인터뷰를 단순 재진술하는 시험과 새로운 상황 시험 구분; withheld 질문/실제 주민 정정 기록. P12 부재 근거는 unknown.
설계 도구 평가: 현재 단회 시뮬레이션/수동 비교와 리뷰 기반 반복의 차이를 같은 세계·자료·과제에서 비교. 대안의 기제 다양성, 근거 연결, 문제 재정의, 과신, 검토 시간, 운영안의 설명 가능성을 평가.
LLM 리뷰의 효과와 자동 patch의 효과는 가능한 한 분리해 조사. 작은 형성 연구는 질적 발견 중심이며 임의 표본수로 통계적 보증을 주장하지 않음.

재방문은 모든 로그 대신 짧은 사건 카드로 진행:
1 사건 설명, 2 모의 반응 공개 전 실제로 어떻게 했을지 질문, 3 모의 리뷰와 비교, 4 운영안 변화에 대한 의견, 5 정정.
참여자가 쉬거나 중단할 수 있고 실제 부담/시간도 기록한다. 인터뷰 횟수 감소와 총부담 감소는 실제로 측정해야 한다.
결과는 agreement/correction/unknown 및 이유·조건으로 저장. 인터뷰 의견은 실제 서비스 사용 경험과도 구분한다.
현장 정정을 사용해 모델을 고친 뒤 같은 문항만으로 정확도 개선을 주장하지 않는다.

## 12. 연구 범위와 선행연구 연결
[추가 문헌](09_DESIGN_POLICY_REFERENCES.md)의 Social Simulacra/Generative Agents 계열은 행위자 기반 탐색, CPD는 기제 설계, PolicyKit은 절차, Companion Modelling은 현장 정정, RDM은 가정별 비교에 참고한다.
이번에 새 문헌 검색을 한 것은 아니며 이전 탐색을 사용자의 최종 연구 루프로 재구성했다.
합성 리뷰는 실제 주민 목소리를 대체하지 않는다. 이 한계가 마지막 재방문과 정정 기능의 설계 이유다.

## 13. 전체 완료의 정의
인터뷰 기반 에이전트와 실제 마을에서 v0 Cycle→개인 리뷰→개선안→v1 Cycle→리뷰→최소3세대의 기록이 연결되고, 디자이너가 과거/분기 대안을 비교해 선택·보류한 후, 실제 사람의 검토와 모델 정정을 저장할 수 있어야 한다.
오프라인 scripted smoke test만으로 'LLM 기반 리뷰 반복 완성'이라고 보고하지 않는다. 실제 LLM adapter와 모드 표시·실패 처리가 필요하다. 외부 키가 없는 환경에서는 미검증 경계를 명시한다.
기관 역할/119/다일 등은 단계적으로 구현하되 지원 범위 밖 의료 서비스도 가능한 범용 도구처럼 표시하지 않는다.

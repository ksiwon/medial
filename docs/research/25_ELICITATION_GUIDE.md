# 25. 채록 가이드 — 시뮬레이션 가능한 공동체를 받아 적는 법

이 문서는 은점마을이 아닌 다른 공동체에서 같은 방법을 다시 쓰려는 사람을 위한 것이다.
시뮬레이터가 결과를 내려면 다섯 가지를 알아야 하는데, 은점마을 인터뷰는 그중 **하나만 물었다.**
나머지 넷은 물은 적이 없으면서도 코드 안에서는 "없음"으로 취급되고 있었다. 2026-09-15에
그 차이를 **채록 장부**(`ledger*.json`)로 옮겼고, 이 문서는 장부를 어떻게 채우는지 적는다.

## 1. 원칙 하나

**"물었고 없다"와 "안 물어봤다"는 다른 사실이다.**

관계 그래프에 P1의 간선이 이장 하나뿐이면, 시뮬레이터는 어떤 연락 순서를 짜도 이장에게
간다. 그 결론이 "P1은 정말 이장밖에 없다"인지 "P1에게 누구에게 도움을 청하는지 묻지 않았다"인지에
따라 연구의 주장이 달라진다. 장부는 사람×항목마다 아래 네 상태 중 하나를 적는다.

| 상태 | 뜻 | 엔진이 어떻게 읽나 |
|---|---|---|
| `recorded` | 물었고 답이 전부 기록에 있다 | 기록을 사실로 쓴다 |
| `partial` | 물었지만 일부만 기록됐다 (이름만, 전사가 끊김) | 기록을 쓰되 결정 사유·비교 화면에 "채록 공백"으로 표시 |
| `asked_none` | 물었고 "없다"고 답했다 | **진짜 없음**으로 쓴다 |
| `not_asked` | 묻지 않았다 | 기록을 쓰되 "없는 것이 아니라 모르는 것"이라고 말한다 |

빈칸을 `asked_none`으로 적는 순간 시뮬레이터는 그것을 마을의 사실로 만든다. 확실하지 않으면
`not_asked`다.

## 2. 다섯 항목 — 무엇을 물어야 하나

| 항목 (`topic`) | 시뮬레이터가 쓰는 곳 | 물어볼 것 |
|---|---|---|
| `companions` 함께 다니는 사람 | 관계 간선(`relations.py`), 넘기기(relay) | "평소에 같이 다니거나 서로 집에 가는 사람이 있나요? 누구요?" |
| `help_contacts` 부탁하거나 도움을 청하는 사람 | 정책 D(`relation_first`)의 순서, "관계가 이장뿐"이라는 결론 | "몸이 안 좋거나 급한 일이 생기면 누구에게 먼저 연락하나요? 이웃 중에는요?" |
| `routine_knowers` 내 평소 일과를 아는 사람 | 빈집 다음에 "어디 계실지"를 누구에게 묻는가 | "이 시간에 어디 계신지 아는 사람이 있나요? 이장님은 아시나요?" |
| `reachability` 연락이 닿는 조건 | 전화·안내 시계가 닿는지(`environment.py`) | "밭에 계실 때 전화 받으세요? 안내 시계 소리는 어디까지 들리나요?" |
| `decline_conditions` 부탁을 못 받는 조건 | 거절 표(`decline_rules`) 첫째 줄 | "이웃이 좀 봐 달라고 하면 못 가는 때가 있나요? 어떤 때요?" |

은점마을 인터뷰는 첫째만 물었다. 둘째·셋째·다섯째는 묻지 않았고, 넷째는 퀘스트 기록(Q3: 밭에서
문진에 응답하지 않음) 하나뿐이다. 그래서 `local-data/normalized/ledger.v1.json` 초안은 대부분
`not_asked`이고, 이것은 데이터의 결함이 아니라 **다음 인터뷰에서 물을 목록**이다.

## 3. 장부 파일

마을 파일 옆에 `ledger*.json`으로 둔다 (`MEDIAL_LEDGER_PATH`로 바꿀 수 있다). 없으면
`ledger-legacy`가 되어 모두 `not_asked`, 이장이 전원의 일과를 안다고 **가정**한 채로 돈다 — 옛
실행과 같은 결과를 내되 공백이 화면에 보인다.

```json
{
  "id": "ledger-eunjeom-v1",
  "label": "…",
  "entries": [
    {"actorId": "P1", "topic": "companions", "status": "asked_none",
     "basis": "인터뷰 '함께 다니는 이웃' 문항"},
    {"actorId": "P1", "topic": "help_contacts", "status": "not_asked", "basis": ""}
  ],
  "routineKnowledge": [
    {"knowerId": "P6", "subjectId": "P1", "provenance": "source-adapted",
     "reason": "Q3에서 이장이 자택 부재 뒤 밭으로 가서 P1을 찾았다"},
    {"knowerId": "P6", "subjectId": "P2", "provenance": "researcher-assumption",
     "reason": "순찰로 안다고 가정. 현장 확인 필요"}
  ],
  "assumptions": ["…"]
}
```

- `basis`는 확인할 수 있는 곳(문항, 퀘스트, 전사 줄)이다. `not_asked`만 비울 수 있다.
- `routineKnowledge`는 "누가 누구의 평소 장소를 아는가"다. **이장을 코드로 박지 않는다.** 근거가
  없으면 `researcher-assumption`으로 적고, 그 쌍에 기댄 결정은 화면에 "가정에 기댐"으로 보인다.
- 사람 id는 마을 파일과 같아야 한다. 모르는 id가 있으면 로드에서 거부한다.
- 실명·별명은 어디에도 넣지 않는다. `basis`에도 P번호만 쓴다.

## 4. 결과에 어떻게 나타나나

- 실행마다 `metrics.elicitation`: 그날 관련된 사람들의 공백(`gaps`), 결정이 실제로 기댄
  가정(`leanedOn`). 비교 화면 "기록에 없던 것" 행.
- 장부는 attempt 입력 해시에 들어간다. 장부가 다른 두 실행은 통제 비교가 아니다.
- 정책 D의 결정 사유는 상태를 그대로 말한다: "누구에게 도움을 청하는지는 묻지 않았다 (채록
  공백) — 없는 것이 아니라 모르는 것이다."

## 5. 다른 공동체로 옮길 때 순서

1. 다섯 항목을 **전원에게** 묻는다. 안 물은 사람은 `not_asked`로 남긴다.
2. 함께 다니는 사람·도움을 청하는 사람에서 관계 간선을 만든다. 근거 없는 간선은 만들지 않는다.
3. "일과를 아는 사람"에서 `routineKnowledge`를 만든다. 이장 같은 중심 인물이 없으면 비어 있어도
   된다 — 그러면 빈집 다음 단계가 "물을 사람 없음"으로 끝나고, 그것이 그 공동체의 결과다.
4. 연락 조건은 환경 규칙으로, 거절 조건은 거절 표 첫째 줄로 옮긴다. 둘 다 `provenance`를 단다.
5. 장부를 마을 파일 옆에 두고 한 번 돌려, 비교 화면의 "기록에 없던 것"이 인터뷰 계획과 맞는지 본다.
